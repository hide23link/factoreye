# 機器シミュレータ（device_sim）

OSS 版の取り込み（機器ごとのキー・`samples` 形式）に、**現場の機器の送信を再現**して、取り込み側（ラズパイなど）の負荷と、保存したデータの欠け・重複を確かめる。

- 1 プロセス（コンテナ） = 1 か所 = 3 要素（電圧 V・電流 A・電位 V）。1 秒ごとに測り、「時刻（秒単位）+ 3 要素」を送る
- 値は、か所ごとの基準値に戻りながら、乱数で上下する（まれに大きめの揺れが入る）
- 機器ごとのキー（`X-Device-Key`）で送る。送信が失敗したら、その秒のデータを溜めて、次の送信でまとめて再送する（時刻つきなので二重にならない）
- 既存の [`emulator/`](../emulator)（SaaS の利用者の送信と画面の閲覧を再現する）とは別の道具

## 送り方（`MODE`）

| MODE | 動き | 1 か所あたりのリクエスト |
|---|---|---|
| `second` | 1 秒ごとに、その秒の 3 要素を 1 回送る | 毎秒 1 回 |
| `batch`（既定） | 1 秒ごとに測り、`BATCH_SECONDS`（既定 60）個ためて、1 回で送る | 60 秒に 1 回（1 回 60 時刻 × 3 要素） |

多数の機器が同じ瞬間に送らないよう、`second` は 0〜1 秒、`batch` は 1 分の中で均等に、送る位置をずらす。

## 前提

- 取り込み側（OSS 版）: `INGEST_DEVICE_TIME=on`。多数の機器が同じ IP から送る試験では、`INGEST_RATE_LIMIT=off`（既定の 100 回/分に当たるため）
- 送信側: Docker。準備と監視は、取り込み側へ ssh できること（取り込み側の Docker で動く backend のコンテナの中で、センサーと機器を作る）
- **本番（SaaS）には使わない**。機器ごとのキーは OSS 版だけの機能で、試験用のセンサーが残る

## 手順

以下は `loadtest/device_sim/scripts` で実行する（`TARGET` と URL は、自分の環境の値に置き換える）。

```bash
export TARGET=user@192.0.2.10                  # 取り込み側の ssh の宛先（空なら、このマシンの Docker）
export KEYS_DIR=./keys LOGS_DIR=./logs
URL=http://192.0.2.10:8001/api/ingest/readings

# 1. 準備: 100 か所分のセンサー（ld01-v/-i/-e …）と機器（r-load-01 …）を作り、キーを KEYS_DIR に保存する
./setup_devices.sh 100 "$KEYS_DIR"

# 2. 実行: 例は、100 か所が 60 個を 1 分ごとに送る、1 時間（秒数は DURATION）
./run.sh 100 batch 3600 "$URL"        # 1 秒ごとなら: ./run.sh 100 second 3600 "$URL"

# 3. 監視（任意）: 取り込み側の load・温度・メモリ・CPU・測定値の件数を記録する（25 秒おきに 150 回）
./monitor.sh 150 25 "$LOGS_DIR/monitor.log" &

# 4. 経過: 各コンテナのログ（成功・失敗・溜め・応答時間）
docker logs devsim-50 | tail -3            # 全体の集計は、LOGS_DIR/sim-ld*.log にもある

# 5. 止める（途中でやめるときも）
./stop.sh
```

### 結果の確認（欠け・重複）

`check.sql` は、各か所の電圧について、件数・時間の幅（秒）・重ならない時刻の数が一致するか（＝欠けも重複もないか）を確かめる。**試験ごとに、開始より少し前の時刻を `since` に指定する**（前の試験との空白を、欠けと数えないため）。

```bash
PSQL='docker exec -i factoreye-postgres-1 sh -c "psql -U \$POSTGRES_USER \$POSTGRES_DB -At -F \" | \""'
sed "s/:since/'2026-10-30 11:00:00+00'/" check.sql | ssh "$TARGET" "$PSQL"
# 出力: か所の数 | 合計件数 | 最小 | 最大 | 欠け・重複のないか所 | 欠けた秒の合計 、続けて 全体の件数 | 重ならない件数
```

止めるのに時間がかかるため、`stop.sh` の少し後の時刻まで保存されることがある（問題ではない）。最後の端数（`DURATION` が `BATCH_SECONDS` で割り切れないとき）は、終了時に送られる。

### 後片付け（必ず行う）

```bash
ssh "$TARGET" "$PSQL" < cleanup.sql          # 試験で作ったセンサー・測定値・機器だけを消す
rm -rf "$KEYS_DIR"                           # 機器のキー（秘密）を消す
```

## 注意

- **キーは秘密**。`KEYS_DIR` のファイルは権限 600 で、画面にもログにも出さない。試験が終わったら消す
- **画面の負荷**: センサーを多数作ると、ダッシュボードやセンサー棚を開いたブラウザが、センサーごとに推移データを取りにいく（300 個で、Cloudflare Tunnel 経由でも 1 分あたり 約 340〜370 件）。試験中は画面を閉じるか、試験後すぐに `cleanup.sql` を実行する
- Mac の Docker で長時間行うときは、`caffeinate -dimsu -t <秒>` でスリープを防ぐ
- 取り込み側の設定を一時的に変えたとき（`INGEST_RATE_LIMIT=off`、`--workers` など）は、試験後に戻す

## 結果の目安（2026-10-30、ラズパイ 4 コア・LAN 直接）

| 送り方 | 台数 | バックエンド CPU（最大） | 応答（平均） | 結果 |
|---|---|---|---|---|
| 1 秒ごと | 10 | 44% | 約 22 ms | 失敗 0 |
| 60 個を 1 分ごと | 100 | 28% | 約 72 ms | 失敗 0 |
| 1 秒ごと（キャッシュ無し） | 100 | 約 100%（飽和） | 約 1.4 秒 | タイムアウトで失敗あり（溜めて再送。欠けなし） |
| 1 秒ごと（照合のキャッシュ） | 100 | 平均 92% | 約 180 ms | 失敗 0 |
| 1 秒ごと（`--workers 4`） | 100 | 平均 194%（4 つに分散） | 約 45 ms | 失敗 0 |

どの試験も、保存したデータに欠けも重複もなかった。運用（60 秒ごとのまとめ送り）なら 100 か所でも余裕があり、1 秒ごとは約 70 か所が 1 プロセスの限界（キャッシュで 100 か所まで）。

## 開発

```bash
cd loadtest
pytest tests/test_device_sim.py        # 値の生成・送信の位置・本文の形・再送（手元の簡易サーバーに送る。外部サービス不要）
python -m device_sim                   # 環境変数で設定（__main__.py の冒頭を参照）
```
