# FactorEye 負荷テストエミュレータ

同時 20〜50 ユーザーがセンサーを送信し、画面を閲覧・設定変更する状況を再現する。
想定（ユーザー数・センサー数・送信間隔など）は Web 画面から、実行中でも変更できる。

## 想定の既定値

| 項目 | 既定値 | 範囲 |
|---|---|---|
| 同時ユーザー数 | 20 | 1〜100 |
| 1ユーザーあたりのセンサー数 | 5 | 1〜10（無料プランの上限に合わせた） |
| 送信間隔 | 5 秒 | 0.1〜60 秒 |
| 送信のゆらぎ | 0.5 秒 | 0〜5 秒（間隔以下） |
| 閲覧の並行数（1ユーザーあたり） | 1 | 0〜10 |
| 閲覧の間隔 | 3 秒 | 0.1〜60 秒 |
| 値の傾向 | sine | sine / random / spiky（spiky はアラームを発生させる） |

送信は 1 リクエストにつき 1 センサーの値（既存の取り込み API の形）。
20 ユーザー × 5 センサーなら約 20 リクエスト/秒、50 ユーザー × 10 センサーなら約 100 リクエスト/秒になる。

> OSS 版の機器（機器ごとのキー・1 秒サンプリング）の送信を再現する別の道具は、[`device_sim/`](device_sim/README.md)。

## 起動

```bash
cd loadtest
pip install -r requirements.txt
python -m emulator            # http://127.0.0.1:8100 で画面を開く
pytest                        # 単体テスト（外部サービス不要）
```

画面の「想定」を変えて「想定を反映」すると、実行中なら即座に反映される（対象URLの変更だけは再起動になる）。
「開始」「停止」「計測をリセット」で実行を制御する。

## 安全のための制限

- **本番かもしれないホストへの実行は拒否する**（手元・社内・試験用と分かるもの＝`localhost`・`192.168.x.x` などの私的なアドレス・ドットのない名前・`.local` などだけを通す。それ以外の公開ホストは、本番とみなす。`emulator/scenario.py` の `is_production_target`）。どうしても必要な場合のみ「本番ホストへの実行を許可」を付ける。事前に運用者の承認を得ること。
- 既定では `127.0.0.1` にだけ待ち受ける。外部に公開すると、誰でも負荷をかけられてしまう。
- 後片付けは、管理者 ID とパスワードで管理者 API を使い、負荷テスト用のユーザーだけを削除する（メールが `接頭辞-実行ID-番号@example.com` に一致するものだけ）。

## OSS 版（self-hosted）に向ける場合

想定に `oss_mode`（true）と `ingest_api_key`（対象の `INGEST_API_KEY`）を指定する。認証がないため、ユーザーの登録・ログイン・ダッシュボードの作成を省き、取り込みを `X-API-Key` で送る。`oss_mode` では `ingest_api_key` が必須。対象 URL か、この 2 つを変えると再起動になる。

## 計測

API ごとに件数・エラー数・p50/p95/p99 のレイテンシ、直近 10 秒のリクエスト/秒、エラー率を表示する。
429（レート制限）も 5xx も通信失敗も、すべてエラーとして数える。

## 既知の制約（重要）

**取り込み API は IP ごとに 100 回/分のレート制限がある**（`INGEST_RATE_LIMIT`、既定 `100/minute`）。
1 台のエミュレータは全センサーを同じ IP から送るため、この制限に当たり、取り込みの約半数が 429 になる（実測: 20 ユーザー × 5 センサー、既定値のまま → 取り込みの 55% がエラー）。

負荷テストでは、バックエンドの環境変数 `INGEST_RATE_LIMIT` で制限を緩める（`"1000000/minute"`、または `"off"` で解除。解除すると起動時にログで警告が出る）。

- **OSS 版**（`docker-compose.yml`）: `INGEST_RATE_LIMIT` は compose が backend に渡す。`.env`（compose と同じ階層）に `INGEST_RATE_LIMIT=off` と書いて `docker compose up -d` し直す。未指定なら `100/minute` のまま。
- **クラウド版**（`docker-compose.cloud.yml`）: compose は `INGEST_RATE_LIMIT` を渡さないため、`.env` に書いても効かない。本番の制限を誤って外さないための意図的な仕様で、緩めたいときは管理画面の期限付き解除を使う。
- 上記の compose を使わず backend を直接起動する場合は、シェルの環境変数として渡す。

本番でも、工場のゲートウェイ 1 台に多数のセンサーを束ねる構成では、同じ制限に当たる可能性がある。
制限値の見直し、またはゲートウェイ単位の制限への変更を検討すること（現状は未対応）。

## 制約

- エミュレータ 1 台の性能に依存する。50 ユーザー × 10 センサー（約 130 リクエスト/秒）が上限の目安で、その時点でもエミュレータ側の CPU が先に飽和しないか確認すること。
- 新規ユーザーの登録が一度に集中すると、取り込みのレイテンシが一時的に上がる（実測: 30 ユーザー追加直後の p95 が約 590 ms、その後 10 ms 台に戻る）。
- 無料プランの上限（10 センサー/ユーザー）を超える設定は、センサー作成が 402 で止まる。
