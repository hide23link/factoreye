# 機器ごとのキー（自前ホスト向け）

機器（現場の 1 台）ごとにキーを発行し、そのキーで送った値は、その機器に所属するセンサーにだけ保存されます。共通の API キー 1 つを全機器に配るより、1 台が漏れたときの影響を、その機器だけに抑えられます。

- **対象**: 自前ホスト（`AUTH_MODE=disabled`、OSS 版）だけです。SaaS 版では使えず、`X-Device-Key` は無視されます。
- **仕様の正**: [`architecture.md`](architecture.md) §5（取り込み）。判断の経緯は [`decisions.md`](decisions.md)（2026-10-30）。

## 1. 機器を作り、キーを控える

backend のコンテナの中で実行します。

```bash
docker compose exec backend python -m app.device_cli create <機器名>
```

キーが 1 回だけ表示されます。**その場で控えてください。** DB にはハッシュしか残らず、あとから表示し直すことはできません。忘れた場合は、新しい機器を作り直します（§3）。

機器名は一意です。同じ名前があると、`create` は終了コード 1 で止まります。

## 2. センサーを機器に所属させる

```bash
docker compose exec backend python -m app.device_cli attach <機器名> <ingestKey> [<ingestKey> ...]
```

- 所属させたセンサーには、その機器のキーでしか送れなくなります。
- 見つからない ingestKey があると、残りは所属させたうえで、終了コード 1 で終わります（見つからなかったものを stderr に表示）。
- 1 つのセンサーは、1 つの機器にだけ所属します。別の機器に `attach` すると、所属が付け替わります。

## 3. 機器側の設定

機器は、取り込みの API に次のヘッダーを付けて送ります。

```
POST /api/ingest/readings
X-Device-Key: <発行されたキー>
Content-Type: application/json
```

- `X-Device-Key` があれば、共通の `X-API-Key` は要りません（共通キーを機器に入れなくてよくなります）。
- 本文は、従来の形（`ingestKey` / `sensors` / `samples`）のまま使えます。

## 4. 応答の意味

| 応答 | 意味 | 対処 |
|---|---|---|
| 202 | 受け付けた（`rejected` が空） | — |
| 202 + `rejected` の `status: 401` | 所属のあるセンサーに、機器のキー無しで送った（`sensors`・`samples` の形） | 機器のキーを付けて送る |
| 202 + `rejected` の `status: 403` | ほかの機器のセンサー、または、どの機器にも所属していないセンサーに送った | `attach` で所属させる、または機器を確認する |
| 401 `invalid device key` | キーが違う、または失効している | キーを確認する。失効したなら、§5 |
| 401 `device key (X-Device-Key) is required` | 所属のあるセンサーに、キー無しで送った（単発の形） | `X-Device-Key` を付ける |
| 403 `sensor is not attached to this device` | 機器のキーで、ほかの機器のセンサー、または未登録のセンサーに送った | `attach` で所属させる（未登録なら、先にセンサーを作る） |

未登録のセンサーは、機器のキーでは自動で作られません（`INGEST_AUTO_CREATE=on` でも）。先に画面かAPIでセンサーを作るか、`INGEST_AUTO_CREATE=on` で機器のキー無しの送信でいったん作ってから `attach` してください。

## 5. キーの失効と再発行

キーの再発行のコマンドはありません。キーを変える場合は、新しい機器を作ります。

1. 旧キーを失効させる（漏れたとき、または機器を廃棄するとき）:
   ```bash
   docker compose exec backend python -m app.device_cli revoke <機器名>
   ```
   失効したキーは、すぐに 401 になります。
2. 新しい機器を作り、キーを控える（§1）。
3. 所属させ直す（§2）。`attach` は所属を付け替えるので、旧機器のセンサーを新しい機器の名前で `attach` し直します。

**注意**: 失効させても、センサーの所属は残ります。新しい機器に `attach` し直すまで、そのセンサーには誰も送れません（キー無しは 401、旧キーは 401）。キーを失効させる前に、新しい機器の準備を済ませてください。

## 6. 機器の一覧

```bash
docker compose exec backend python -m app.device_cli list
```

機器名、有効か失効か、所属のセンサーの数、作成日時を表示します。キーは表示しません。

## 7. 運用の注意

- **キーの扱い**: キーは、発行の画面（標準出力）にだけ出ます。ログには出ません。機器の設定ファイルに書く以外は、どこにも残さないでください。
- **CLI のログ**: `ENVIRONMENT=production` にすると、SQL のログが出なくなり、キーの行が見つけやすくなります。開発用の既定（`development`）では、SQL のログが混ざります。
- **機器の削除**: CLI に機器の削除はありません。DB で機器の行を直接削除すると、センサーの所属は外れます（`SET NULL`）。所属が外れたセンサーは、キー無しで送れるようになります。機器の廃棄は、`revoke` を使ってください。
- **SaaS との違い**: SaaS 版の DB に、この CLI を使わないでください。CLI は自前ホストでだけ動き（SaaS の設定では終了コード 1）、所属も SaaS では無視されます。
- **共通キー**: `INGEST_AUTH=key` のとき、機器のキーを使わない送信には、従来どおり共通の `X-API-Key` が要ります。所属のないセンサーは、従来どおりの扱いです。
