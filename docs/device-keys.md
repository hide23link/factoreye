# 機器ごとのキー（self-hosted 向け）

機器（現場の 1 台）ごとにキーを発行し、そのキーで送った値は、その機器に所属するセンサーにだけ保存されます。共通の API キーを全機器に配るより、1 台が漏れたときの影響をその機器だけに抑えられます。

- **対象**: self-hosted（`AUTH_MODE=disabled`）だけです。SaaS では `X-Device-Key` は無視されます
- **仕様**: [`architecture.md`](architecture.md) §5

画面（設定 → 機器）からも、追加・センサーの所属・失効・削除ができます。以下はコマンドでの手順です（backend のコンテナの中で実行）。

## 使い方

```bash
# 1. 機器を作る。キーは 1 回だけ表示されるので、その場で控える（--line で系統も付けられる）
docker compose exec backend python -m app.device_cli create <機器名> [--line 第1ライン]

# 2. センサーを機器に所属させる（別の機器に attach すると付け替わる）
docker compose exec backend python -m app.device_cli attach <機器名> <ingestKey> [<ingestKey> ...]

# 3. 機器の一覧（名前・有効/失効・センサー数・系統・キーの目印・作成日時）
docker compose exec backend python -m app.device_cli list
```

機器側は、`X-Device-Key: <キー>` を付けて `POST /api/ingest/readings` に送ります。共通の `X-API-Key` は要りません。

- キーは DB にハッシュと先頭 6 文字の目印しか残らず、表示し直せません。忘れたら新しい機器を作り直します
- 機器名は一意です
- **系統**は任意の区分（例: 第1ライン、40 文字まで）で、センサー棚の「系統 › 機器 › センサー」に使います。後から変えるには `set-line <機器名> [系統]`（系統を省くと外す）
- 未登録のセンサーは、機器のキーでは自動で作られません。先にセンサーを作ってから `attach` してください

## 応答

| 応答 | 意味 | 対処 |
|---|---|---|
| 202 | 受け付けた | — |
| 202 + `rejected` の 401 | 所属のあるセンサーに、キー無しで送った（`sensors`・`samples`） | 機器のキーを付ける |
| 202 + `rejected` の 403 | ほかの機器、または所属のないセンサーに送った | `attach` で所属させる |
| 401 | キーが違う、または失効している | キーを確認する |
| 403 | 機器のキーで、ほかの機器・未登録のセンサーに送った | `attach` で所属させる |

## キーの失効と再発行

再発行のコマンドはありません。キーを変えるときは、新しい機器を作ります。

1. 新しい機器を作ってキーを控え、センサーを `attach` し直す（付け替わります）
2. 旧機器を失効させる: `python -m app.device_cli revoke <機器名>`（すぐ 401 になります）

失効させてもセンサーの所属は残るので、新しい機器の準備を先に済ませてください。

## 注意

- 失効した機器だけ、`delete <機器名>`（画面では「この機器を削除」）で削除できます。センサーと測定値は残り、センサーの所属が外れて**キー無しで送れる状態に戻ります**
- 所属のないセンサーは、従来どおり共通の `X-API-Key` で送ります
- SaaS の DB には、この CLI を使わないでください
