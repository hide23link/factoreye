### 2026-10-02: Pluginシステムの基盤実装（Sprint 6 backend）

**背景**: ロードマップのSprint 6に着手。Sprint 5と同様、まずbackendを実装し、frontend（設定UI・ウィザード）は次回に分けた。

**実装内容**:
- `app/plugins/base.py`: プラグインの型定義（`FactorEyePlugin`）と、全フックが空実装の`BasePlugin`。プラグイン作者は必要なフックだけ書けば済む
- `app/plugins/registry.py`: `app/plugins/installed/`配下を自動スキャンして発見する仕組み。1つのプラグインが壊れていても起動全体を落とさない
- `app/plugins/manager.py`: 発見→DB登録→有効なものだけ起動→APIルートをマウント→読み取りデータの配送、という流れを管理。同じ処理を複数回呼んでも安全（冪等）
- `app/api/plugins.py`: 一覧・有効化/無効化・設定変更のAPIを追加
- `app/ingest_buffer.py`: センサー値の書き込み後、起動中の全プラグインに通知するよう接続
- サンプルプラグイン`reading_logger`を、最小限の実装例として追加

**設計書との食い違いを2点解決**（設計書側は未更新・要反映）:
- 新規プラグインの初期状態は設計書の図では「有効」だったが、実装は「無効」が正しい。サンドボックスが無い以上、未知のプラグインを自動で有効化しない安全側の判断とした
- プラグイン名は設計書ではkebab-caseの例だったが、フォルダ名がPythonパッケージ名と一致する必要があるためsnake_caseを採用した。フォルダ名とプラグイン名が一致することはコードで検証する

**既知の制限**（設計書の「既知のリスク」の記述と整合済み）:
- 無効化してもFastAPIの制約でHTTPルート自体は残る（再起動まで）。止まるのはデータの配送だけ
- サンドボックスなし。エラーは各フック呼び出し単位でログに残して握りつぶし、1つの不具合で他のプラグインや全体を止めない設計

**確認方法**: CIと同じ手順（pytest・mypy・ruff・pip-audit）を本物のpostgresコンテナで実行した。pytest 28件全通過、mypy・ruffともにエラーなし（pip-auditの検出はベースイメージ側の既知脆弱性のみで、本プロジェクトの依存関係には問題なし）。ブラウザでの確認はまだ無し（frontend UIが無いため、次回まとめて行う）。

**次フェーズ（未着手）**: Plugin設定UI、Quick Setup Wizard、Sensor/Alarm/Dashboard設定画面。

### 2026-10-02: 【事故】pytestが開発用DBの全テーブルを削除していた問題

**何が起きたか**: 「`alembic_version`だけ残る」現象の本当の原因が判明した。`backend/tests/conftest.py`のテスト用フィクスチャは、テスト終了時に全テーブルを削除する（テスト専用DBに対しては正しい動作）。しかし、このセッション中は`DATABASE_URL`を**開発者が実際に使っている本物のpostgresコンテナ**にそのまま向けてしまっていた。そのため、pytestを実行するたびに**プロジェクトリードがブラウザで作成したセンサー・ダッシュボードのデータが丸ごと消えていた**。`alembic_version`テーブルだけ残ったのは、削除対象の管理下に無かったためである。

**影響**: プロジェクトリードが手動で作成したデータが複数回失われた（バックアップなし、復元不可）。実害があったことをお詫びし、ここに記録する。

**再発防止**:
- テスト専用のDB（`factoreye_test`）をpostgresコンテナ内に作成した
- 以後、dockerでbackendテストを実行する際は、`DATABASE_URL`の接続先DB名を必ず`factoreye_test`にする
- CI（GitHub Actions）は専用のpostgresコンテナを都度起動するため、この問題は起きない（ローカルで開発用DBに相乗りする時のみ注意が必要）

### 2026-10-02: qa-agentレビューで発覚したCritical/High修正（Sprint 7の続き）

**背景**: 独立したレビューセッションのqa-agentが、フレッシュな状態（直前の事故でボリュームが空になった状態）で`docker compose up --build`を実行し、再現性のある重大バグを発見した。

**Critical: フレッシュなDBではbackendが起動時にクラッシュする**
- 症状: `UndefinedTableError`（`plugins`テーブルが無い）でクラッシュループする
- 原因: `backend/Dockerfile`に`alembic upgrade head`（DBマイグレーション適用）を実行する手順が無かった。既存のボリュームには過去の手動適用結果が残っていたため、今回のボリューム消失事故が起きるまで誰も気づかなかった
- 影響: 新設した`e2e-test.yml`はGitHub Actionsの完全にフレッシュなrunnerで動くため、このままでは初回実行が確実に失敗する
- **修正**: Dockerfileの起動コマンドを`alembic upgrade head && uvicorn ...`に変更した
- 検証: ローカルでのDocker操作が（直前の事故を踏まえ）権限でブロックされ再検証できなかったため、修正をpushしてGitHub Actions上のフレッシュなrunnerで直接検証する方針に切り替えた

**High: アラーム確認（ack）のテストが実質何も検証していなかった**
- 原因: ボタン名「確認済み」での要素取得が、常時表示されているステータス絞り込みタブ（同じ文言）に誤ってヒットしており、ackの成否を何も検証できていなかった（たまたま毎回パスしていた）
- **修正**: ack後に「発生中」一覧からその行が消えることを確認してから、「確認済み」タブへの遷移を確認する形に変更した

**Low（対応済み）**: `e2e-test.yml`にpathsフィルタを追加した（backend/frontend/e2e関連の変更時のみ起動するように）

**Low（Sprint 8バックログへ）**:
- frontendのカバレッジ計測ツールが未導入で、数値目標（70%以上/最低50%）を検証できない
- `SetupWizard.tsx`等の主要コンポーネントと`lib/api.ts`の大半の関数が単体テスト0件のまま（E2Eでのみ間接的にカバー）
- 自宅LXCのrunner移行時、`docker compose down -v`がrunner間で共有されるdockerホスト上で動くと、project名の衝突により同種の事故がCI経由でも起こりうる。移行時に専用project名を使うようinfra-agentへ申し送り

**GitHub Actionsのフレッシュなrunnerで検証した結果、さらに2件のバグが見つかった**（ローカルの使い回しDBでは踏まない、フレッシュ環境特有の問題）:
1. ヘルスチェック待ちが実質機能していなかった。`curl --retry-connrefused`は「接続拒否」のみ再試行の対象で、「ポートは開いているがアプリがまだ起動準備中」のエラーは対象外だった。失敗を無視してsleepを挟みながら最大40回試す、単純なループに変更して解決した
2. ダッシュボード0件のとき、セットアップガイドへの誘導ボタンが2つ同時にヒットしてテストが失敗した。ヘッダーnavのボタンと、一覧画面のCTAボタンが同じ文言のため、部分一致検索で衝突していた。ローカルでは既存ダッシュボードがあり0件状態に遭遇しなかったため見逃していた。nav要素内に絞る指定に修正した

**教訓**: 「ローカルの使い回しDB」と「フレッシュな環境（CI・新規ユーザー）」で挙動が変わる箇所が3つ見つかった（マイグレーション未適用・ヘルスチェックの競合状態・ダッシュボード0件時のUI分岐）。E2E/統合テストは一度はフレッシュな状態で通しておくべき、というのが今回最大の学びである。最終的にGitHub Actions上のフレッシュなrunnerで3シナリオ連続グリーンを確認済み（commit `67ff51b`）。

### 2026-10-02: センサー削除を論理削除→物理削除に変更

**背景**: デモ中にエミュレータのセンサーを削除し、同じ名前で再登録しようとしたら失敗した（409エラー）。原因は論理削除方式の既知の制限で、削除済み行にも名前の重複禁止制約が及んでいたためである。プロジェクトリードに3択を提示して確認し、「アラーム履歴が一緒に消えるリスクを許容してでも完全削除にする」で合意した。

**実装内容**:
- センサーの削除を物理削除に変更した（論理削除用の`deleted_at`は廃止）
- 削除時、測定値とアラームはまとめて消える（CASCADE）。ウィジェットはセンサーとの紐付けだけ外れ、ウィジェット自体は残る（SET NULL）
- 一覧表示・検索から論理削除用のフィルタを除去した
- 削除確認ダイアログの文言を「履歴は保持されます」→「測定値・アラーム履歴も完全に削除されます。元に戻せません」に修正した（実態と一致させた）
- テスト3件を追加した（名前の再利用が成功すること・測定値とアラームが連動削除されること・ウィジェットは紐付けだけ外れて残ること）。55件全通過

**ハマりどころ**: DBの削除連動設定（CASCADE）だけでは不十分だった。SQLAlchemyが削除前に関連データを読み込んでFKをNULLにしようとする既定動作のせいで、本来NULLを許さないはずのアラームのセンサーIDが書き換わっていた（テストで発覚）。関連設定に`passive_deletes: True`を追加し、DB側の連動削除に任せることで解決した。

**対象外**: ダッシュボードの論理削除はそのまま変更していない。今回の問題はセンサー特有のもので、ダッシュボードには影響せず、変更依頼も無かったためである。

**次フェーズ**: pushしてCI全部（backend-test / frontend-build / e2e-test）がグリーンになることを確認する。
