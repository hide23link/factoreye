## 製品方針

### 2026-10-01 — 拡張は Python プラグインではなく Webhook で行う
- **判断**: 業種別の拡張は、Webhook（イベントを JSON で送る）とルール設定で実現する
- **理由**: 対象は技術者でない工場スタッフ。プラグインは Python を書く必要があり、安全に配布する仕組み（サンドボックス）も無い。Webhook なら Zapier・Make・n8n などでコード無しに連携できる
- **影響**: プラグイン基盤（10-02 導入）は 10-04 に廃止。詳細は [Webhook・通知](#webhook通知)

### 2026-10-02 — 通知は Discord Webhook のみ。設定は DB に持つ
- **判断**: 基本機能の通知は Discord Webhook だけにし、SMTP（Email）は削除した。Discord の URL・有効/無効・再通知の設定は、`.env` ではなく DB に保存し、設定画面から変えられる
- **理由**: 記録なし（プロジェクトの方針）
- **影響**: 他サービスへの通知は Webhook で行う。通知設定がワークスペースごとになった経緯は [認証・SaaS](#認証saas)

### 2026-10-29 — 残務を閉じる。推奨の判断を採り、残りは見送りとして一覧にする
- **判断**
  - `GET /api/readings` は、画面からは呼ばれていない公開 API として残す
  - 有料プランのセンサー上限は、仕様が決まるまで見送る（判定は Free Tier の固定 10 個）
  - 本番の外への控えは `offsite-pull.sh` で稼働中のため、`offsite-s3.sh` の実機確認は行わない
  - 空の本番へ戻す `restore-prod.sh` は作らない（R2 からの復旧は管理画面で 2026-10-29 に確認済み）
  - 残りの制限（ゲートウェイ単位の取り込み制限、メール存在確認の方針、管理画面のページング、Webhook の再試行、モーダルのアクセシビリティ、認証の同時負荷、`refresh_tokens.expires_at` の索引、TimescaleDB、self-hosted の保持期間）は見送る。`architecture.md` §13 に一覧として残す
- **理由**: 利用者がまだ少なく、どれも利用者が増えたときに判断するもの。ユーザー（プロジェクトリード）が推奨どおりで承認した
- **影響**: 今後は、利用者の増加や有料プランの仕様が決まったときに、§13 から見直す

## データモデル

### 2026-10-02 — DB は PostgreSQL 15 のみ
- **判断**: 開発・テスト・本番のすべてで PostgreSQL 15 を使う（テストも PostgreSQL に接続する）
- **理由**: 記録なし。当初は開発・テストに SQLite を使う想定だったが、全環境を統一した

### 2026-10-02 — アラームは 2 段階、しきい値は 4 項目、解除には不感帯を置く
- **判断**: 重要度は軽故障（warning）と重故障（critical）の 2 段階。しきい値は「上限・下限」×「軽・重」の 4 項目。発生は閾値を超えた時点で即時、解除は閾値から不感帯の幅だけ戻ったとき（ヒステリシス）
- **理由**: 現場の要望で、「すぐ止める」と「様子を見る」の通知先・通知音を分けたい。不感帯は、閾値付近で値が揺れると発生と解除が繰り返され、通知が溢れるため
- **影響**: 重要度が変わったときは、新規アラームを作らず既存の行を更新する（履歴が増えすぎないため）。3 段階以上が必要になったら再検討する

### 2026-10-02 — センサーは物理削除、ダッシュボードは論理削除
- **判断**: センサーを削除すると、測定値とアラームも削除する（ウィジェットは残し、紐付けだけ外す）。ダッシュボードは `deleted_at` による論理削除のまま
- **理由**: センサーを論理削除にすると、削除済みと同名のセンサーを登録できず利用者が混乱した
- **影響**: アラーム履歴は失われる。監査用に残す要件が出たら再検討する
- **注意**: DB の CASCADE だけでは足りない（SQLAlchemy が削除前に子の行を読み、外部キーを NULL にしようとする）。`passive_deletes` を設定し、DB 側の連動削除に任せている

### 2026-10-02 — 生産数は「時間・日・目標達成率」。OEE は見送り
- **判断**: 「直近 1 時間」「本日累計」「本日の目標達成率」を集計する。OEE は採用しない
- **理由**: OEE には停止理由の記録とシフトのカレンダーが要る。複雑な生産管理は作らないという現時点の方針に反する

### 2026-10-02 — TimescaleDB は見送り
- **判断**: 複合インデックス `(sensor_id, recorded_at)` で対応する
- **再検討の目安**: 測定値が 1,000 万行を超える、またはダッシュボードのクエリが 500 ms を超える
- **追記（2026-10-25、実測）**: 圧縮は 161 B/行 → 約 12 B/行と効果が大きい。ただし ①圧縮済みの塊への `DELETE`/`UPDATE` は既定の上限（10 万行）で失敗する（`purge.py` を `drop_chunks` に変える必要）、②圧縮済みの塊への `INSERT` は素の 1/18 の速さ（復旧ツールの書き戻しが遅い）、③ダンプは拡張なしの PostgreSQL に戻せない（復旧ツール・OSS 版との行き来に影響）、④主キーに時刻が要る。拡張に依存しない方法（次の項目）を先に採ったので、見送りを続ける

### 2026-10-25 — readings の主キーを (sensor_id, recorded_at) に統合する
- **判断**: `readings` から連番の `id` を廃止し、主キーを `(sensor_id, recorded_at)` にする。索引 `ix_reading_sensor_recorded` は主キーの索引と重複するので持たない（マイグレーション `g7b8c9d0e1f2`）。API の応答（`ReadingRead`）からも `id` を外す
- **理由**: 実測（200 万行）で、1 行 161 B → 101 B（約 4 割減）、500 万行の書き込みは 8.3 秒 → 5.6 秒。検索は同等（差は 1 割以内）。拡張は不要で、`pg_dump` / `restore.sh` / 復旧ツールの手順は変わらない。測定値がまだほとんど無く、影響が最小のうちに行った
- **取り込みの扱い**: 以前は 1 回の送信内の複数の値が同じ `recorded_at` を持っていたため、センサーごとに「前に割り当てた最後の時刻」をメモリに覚え、次はそれより 1 マイクロ秒以上進めて割り当てる（`api/ingest.py`）。それでも主キーが重なる場合（複数プロセス、再起動直後に時計が戻る、commit の応答が失われた後の再試行など）は `ON CONFLICT DO NOTHING` で書かずに続け、実際に書けた値だけをアラーム評価・通知・件数に使い、書かなかった件数を警告ログに出す。1 回の flush は 5,000 行ずつの INSERT に区切る（asyncpg は 1 文のパラメータが 32,767 個までで、全行を 1 文にすると 1 万件余りで失敗し続ける）。なお、機器の時刻を使う取り込み（[取り込み](#取り込み)）では、同じ（センサー, 時刻）は後の値で上書きする
- **移行**: 新しいテーブルへ写し、旧データは 1 行も捨てない。同じ (sensor_id, recorded_at) の旧データは、id が小さい 1 行を元の時刻に、残りを空いている時刻まで 1 マイクロ秒ずつずらして入れる。最後に件数を比べ、合わなければ移行全体を取り消す。書き込みを止めるロックを取るので、稼働中のアプリがあるときは実行しない。readings の 2 倍程度の空きが要るため、更新の前に `infra/check-migration-space.sh` で確かめる。downgrade は `id` を時刻順に振り直して戻す
- **保持期間の削除**: `purge.py` は、主キーの組 `(sensor_id, recorded_at)` で絞って消す
- **見送った案**: センサー番号を `smallint`・値を `float4` にする案（83.8 B/行）、BRIN だけにする案（52.2 B/行。センサーが増えると遅くなる見込み）、1 時間 1 行の配列にする案（8.9 B/行。取り込み・アラーム・間引き・復旧ツールの作り直しが要る）。必要になったら再検討する。1 秒サンプリングの保存（R 版）は、この配列案の延長として設計中
- **影響**: スキーマの版が変わるため、適用前のバックアップは、復旧ツールの書き戻し・マージには使えない（同じ版どうしに限る）

### 2026-10-12 — 未使用の `widget_configs` テーブルを削除
- **判断**: ウィジェットの設定は `widgets.config` に持つため、使われていない `widget_configs` をマイグレーション `e5f6a7b8c9d0` で削除する。downgrade では空のテーブルを再作成する。SaaS → OSS の移行と復旧ツールの対象からも外す
- **理由**: 本番・OSS 版とも 0 件で、アプリが書き込む箇所も無かった
- **影響**: スキーマの版が変わる（適用前のバックアップは、書き戻し・マージに使えない）

## 取り込み

### 2026-10-18 — self-hosted の取り込みは、設定でキーなしにできる（`INGEST_AUTH=off`）
- **判断**: 環境変数 `INGEST_AUTH`（`key` / `off`、既定 `key`）を足した。`off` のときは、self-hosted の取り込みで `X-API-Key` を確かめない（送られてきたヘッダーは無視する）。センサーは本文の `ingestKey` だけで識別する（SaaS と同じ）。`off` のときは `INGEST_API_KEY` を使わないので、本番の既定値の検査もしない。SaaS では何も変わらない
- **理由**: 機器（M5Stack など）に、長い共有キーを入れたくない。キーの入力が現場での設定の手間になり、全機器に同じキーを配るため、1 台から漏れると全台に影響する。空のキーを「キーなし」と読み替える案は、設定の入れ忘れで意図せず開いてしまうので避け、明示の設定にした
- **影響**: `off` では、`ingestKey` を知っていれば誰でも値を書ける。取り込みの口を LAN などに限定して使う。起動時に警告をログに出す。IP ごとのレート制限は残るが、鍵は `CF-Connecting-IP` を優先して読むので、プロキシを通らず直接届く経路ではヘッダーの偽装で避けられる（口の前のプロキシで外す）。誤字（`of` など）は起動時にエラー。機器側は、`FactorEyeClient`（Arduino）が、キーが空なら `X-API-Key` を付けない

### 2026-10-19 — self-hosted は、未登録の ingestKey のセンサーを自動で作れる（`INGEST_AUTO_CREATE=on`）。SaaS は対象外
- **判断**: 環境変数 `INGEST_AUTO_CREATE`（既定 `false`）が on のとき、未登録の `ingestKey` を 404 にせず、センサーを自動で作る。機器が本文に付けた `name`・`unit` を使う（拒否せず、制御文字などを除いて整える）。作るのは、`ingestKey` が英数字と `. _ -` で 64 文字まで、かつセンサーの総数（無効なものも数える）が `INGEST_AUTO_CREATE_MAX_SENSORS`（既定 100）未満のときだけ。作る処理は advisory lock で 1 つずつ行う。SaaS（`multi_tenant`）では無視する
- **理由**: 機器を増やすたびに画面でセンサーを登録するのが手間。SaaS は、取り込みが `ingestKey` だけでワークスペースを決めるので、未登録のキーからは作る先が決まらない（使うにはワークスペース単位の機器登録用のキーが要る。別の設計）
- **影響**: on の間は、打ち間違いの ID でもセンサーが増える（上限で止まる）。削除したセンサーも、次の送信でまた作られる。`INGEST_AUTH=off` と組み合わせると、LAN の誰でも上限までセンサーを作れる。起動時に警告を出す。Arduino の `FactorEyeClient` は `setSensorInfo` で名前と単位を結びつけ、最初に送信が成功するまで本文に付ける

### 2026-10-31 — SaaS でも機器の測定時刻を使う（`INGEST_DEVICE_TIME` は SaaS にも効く）
- **判断**: OSS 版と SaaS 版で同じ取り込み API（`samples`・`timestamp`）を使えるように、SaaS でも `INGEST_DEVICE_TIME=on` のとき機器の時刻を使う。2026-10-30 の「SaaS は対象外」を取り消す。
- **理由**: 1 秒データを 5 秒ごとにまとめて送る機器は、時刻を付けないと SaaS で 1 秒ごとの時刻にならない（受信時刻に揃ってしまう）。ユーザーの指示で、API の互換性を優先した。
- **安全装置**: 時刻の範囲（未来 10 秒超・30 日より前は 400、時差なしは 400）はそのまま。ワークスペースは自分のセンサーにしか書けないので、他の利用者の値は変わらない。影響は自分の測定値の時刻と上書き（同じ時刻は後の値で上書き）に限られる。
- **既定**: `INGEST_DEVICE_TIME` の既定は従来どおり `false`。SaaS で使うには、本番の環境変数で `on` にする（デプロイ時に別途判断）。
- **機器ごとのキー（`X-Device-Key`）は、引き続き self-hosted だけ**（SaaS では無視する）。

### 2026-10-30 — 機器の測定時刻を使える（`INGEST_DEVICE_TIME=on`）。self-hosted だけ（※ SaaS は 2026-10-31 に対象に加えた）
- **判断**: 環境変数 `INGEST_DEVICE_TIME`（既定 `false`）が on のとき、各値の `timestamp`（時差つき ISO 8601 か UNIX 秒）を測定値の時刻にする。付けない値は受信時刻。範囲外（未来 10 秒超・30 日より前）や時差なしは、送信全体を 400 にする。既存の API の形は変えない（`timestamp` は、もともと受け付けて無視していた項目）
- **時刻は秒で管理する**: 秒単位に切り捨てて保存し、数値は UNIX 秒だけ受け付ける（ミリ秒の自動判別はしない）。1 秒サンプリングに足りる精度で、送信データも小さい
- **同じ (センサー, 時刻) は、後から来た値で上書きする**（QA 指摘 L-1 の判断。**SaaS にも入る**）: 先に保存された値を残す案から変えた。再送の値が同じなら結果は変わらず、時計の狂った機器で同じ時刻が届いた場合は最後の値が残る
- **理由**: 1 秒サンプリングなど、機器が NTP で合わせた時刻で測り、溜めてまとめ送りする使い方では、受信時刻だと測定時刻とずれる。既定を off にして従来の挙動を保ち、機器の時計を信用できる運用者だけが on にする。SaaS は、他の利用者の機器の時計を信用できないので対象外
- **影響**: 同じ時刻の再送は二重にならない。時計の狂った機器は 400 で気づける（値は捨てられるので、機器側で見張る）。アラームは機器の時刻で評価される

### 2026-10-30 — 現場の機器は、VPN を使わず TLS で直接送る。機器ごとのキーを持つ（承認: ユーザー）
- **判断**: 機器（M5 Atom Lite、または現場のラズパイ）は HTTPS でサーバーへ直接送る。VPN は使わない。機器ごとにキーを発行し、共通の 1 つのキーは使わない。ラズパイを置ける場所では、ラズパイが一時保存を受け持つ（Atom Lite は一時保存が少ないので、圏外が多い場所にはラズパイを置く）
- **実装**: self-hosted だけ（マイグレーション `h8c9d0e1f2a3`、`app/device_keys.py`、`app/device_cli.py`）。`X-Device-Key` ヘッダーで送り、キーは発行時に 1 回だけ表示してハッシュで保存する。所属のあるセンサーは、その機器のキーでしか送れない。SaaS は従来どおり（`ingestKey` で識別）。手順は [`device-keys.md`](device-keys.md)
- **理由**: Atom Lite は VPN を動かすには小さすぎる。格安 SIM はサーバーへ外から届かないことが多い。機器を 1 つずつ区別すれば、1 台のキーが漏れても、ほかの機器は影響を受けない
- **影響**: データ移行・復旧ツールも機器の表を扱う（[データ移行](#データ移行)、[バックアップ・復旧](#バックアップ復旧)）。TLS での公開方法（Cloudflare Tunnel など）は未決定

### 2026-10-30 — 取り込みの照合（機器のキー・センサー）を、5 秒だけ覚える（`INGEST_CACHE_SECONDS`）
- **判断**: 取り込みのたびに DB で行っていた、機器のキーの照合とセンサーの検索を、プロセスの中で 5 秒だけ覚える。0 で無効にできる。覚えるのは見つかった結果だけ。**SaaS にも入る**
- **理由**: ラズパイ（4 コア）で 100 台が 1 秒ごとに送る試験で、バックエンドの 1 プロセスが CPU 100% で飽和した（平均応答 約 1.4 秒、タイムアウトで失敗）。1 リクエストが DB に 2 回問い合わせ、センサーのオブジェクトも組み立てていたため。キャッシュで、失敗 0 件・平均 約 180 ms になった
- **採らなかった案**: `--workers 4`（平均 約 45 ms と余裕は大きいが、アラームが二重に発生しうるため排他ロックが要る。1 秒ごとの多数の送信が必要になったら検討）
- **影響**: 別のプロセス・CLI からの変更（センサーを無効にする、キーを失効させる）は、最大 5 秒遅れて反映される。同じプロセスの変更はすぐ反映する

### 2026-10-30 — OSS 版の運用（IoT SIM のゲートウェイ）では、取り込みの回数制限を解除する
- **判断**: IoT SIM のゲートウェイは同じ IP（キャリアの NAT）から送られるため、IP ごとの制限（既定 100 回/分）に当たる。OSS 版の運用で `INGEST_RATE_LIMIT=off` を設定して解除する。SaaS の既定は変えない
- **理由**: 1 か所ずつ 60 秒ごとに送ると 350 リクエスト/分になる。まとめ送りにしても、同じ IP から多数のゲートウェイが送る。制限は、この用途では誤って止める
- **条件**: 取り込みの口は LAN に限定する（nginx の窓口が私設アドレスだけを通す）。キャリアの回線からインターネット経由で送る場合は、この窓口を使わず、認証（`INGEST_AUTH=key`）と VPN を前提にする
- **影響**: 解除中は 429 が出ない。取り込みの量は機器側の送信間隔で抑える。起動時に警告が出る

### 2026-10-12 — デバイスクライアントの再送ルール
- **判断**: Raspberry Pi と Arduino/M5Stack のクライアントは、エラーの種類で分ける

  | 送信結果 | 動き |
  |---|---|
  | 通信エラー・5xx・408・429 | 再送する。429 の `Retry-After` は、付いていれば最大 5 分まで尊重する（現行の backend は付けない） |
  | 400・422 など、再送しても成功しない 4xx | その送信分を捨てて警告する |
  | 401・403・404（キーの誤り・センサーの無効化・未登録） | 設定の誤りなので、値を捨てずに保持して再送する。1 センサー 10 件まで、超えたら古い値から捨てる。他のセンサーのバックオフとバッファは巻き込まない |
  | NaN・Infinity・型違いの値 | `send()` の入口で捨てる |
- **理由**: 以前は 4xx も再送していたため、NaN を 1 件送ると 400 が続き、そのセンサーは最大約 100 件の間、送れなくなった
- **影響**: センサーを登録する前にデバイスを動かし始めても、登録後に、保持した値（10 件まで）が届く。仕様は architecture.md §9

## 認証・SaaS

### 2026-10-03 — SaaS はマルチテナント（共有 DB + `workspace_id`）
- **判断**: テナントごとに DB を分けず、同じ DB の中でワークスペース単位に分離する
- **理由**: 記録なし
- **self-hosted との関係**: `workspace_id` が `NULL` のデータが self-hosted。`AUTH_MODE`（`disabled` / `multi_tenant`）で切り替える

### 2026-10-03 — Free Tier の制限
- **判断**: センサーは 10 個まで（超過は 402）。測定値は 14 日で削除（SaaS のセンサーのみ。self-hosted は無期限）
- **理由**: 記録なし。超過分は将来の有料プランで対応する方針
- **保持期間の変更（2026-10-28、当初 90 日）**: DR（AWS の控えへの復旧）のデータ量と復旧時間を小さくするため。500 センサー × 5 秒で、DB 全体が約 100 GB → 約 12 GB、最初のベースバックアップの送信が 8〜22 時間 → 約 1〜3 時間になる（ecopower の `docs/aws-dr-wal-design.md`）。14 日より古い測定値は削除され、戻せない。グラフの最長の範囲は 14 日。利用規約の文言も変更した

### 2026-10-03 — 管理者アカウントは DB に入れない
- **判断**: 管理者は、サーバー上のテキストファイル（bcrypt ハッシュ）で管理する
- **理由**: 記録なし。運用者だけが使うアカウントを、利用者のデータと分けるため
- **影響**: ファイルは DB のバックアップに含まれない。別に保管する

### 2026-10-04 — センサー名はワークスペース内で一意、取り込みキーは全体で一意
- **判断**: センサー名はワークスペース内で一意（self-hosted は NULL 用の部分インデックス）。取り込みキー（`ingest_key`）は全体で一意のまま
- **理由**: 名前を全体で一意にしていたため、別のワークスペースが同じ名前を使えなかった。取り込み API はキーだけでセンサーを特定するので、キーは全体で一意である必要がある
- **影響**: 他のワークスペースのキーと衝突すると 409 を返す。その応答から、キーが使われていることが分かる。ワークスペースごとにキーを分けるには、取り込みの形式を変える必要がある

### 2026-10-04 — 通知設定はワークスペースごとに 1 行
- **判断**: アラームは、そのセンサーのワークスペースの設定で送る。設定が無いワークスペースは、Discord 通知をしない。再通知の判定も、そのワークスペースの設定に従う
- **理由**: ID=1 の 1 行に固定していたため、SaaS のアラームが他のワークスペースの設定で送られるおそれがあった

### 2026-10-04 — リフレッシュトークンは使うたびにローテーション
- **判断**: 使ったトークンは即時に失効し、新しいトークンを発行する
- **理由**: 盗まれたトークンの再利用を見つけやすくするため
- **影響**: 失効済みトークンの再利用を検知する仕組みは無く、401 を返すだけ

### 2026-10-12 — メールは小文字にそろえ、`lower(email)` の一意インデックスで重複を防ぐ
- **判断**: 登録・ログイン・管理者のメール修正では、前後の空白を除いて小文字にし、DB との比較は `lower(email)` で行う。マイグレーション `a7b8c9d0e1f2` で `users(lower(email))` の一意インデックス `ix_users_email_lower` を足す。大文字小文字だけが違う重複が既にあると、重複したメールを示してマイグレーションが失敗する（何も削除しない）。同時登録による一意制約違反は 409
- **理由**: 以前は、大文字小文字が違うメールが別のアカウントになった。`lower()` で比較すると素の列のインデックスが使われず、ログインのたびに全件を走査する
- **影響**: 復旧ツールのマージで、大文字小文字だけが違うメールが両側にあると失敗する。登録時の「既に登録されている」という応答から、登録の有無が分かる点は、方針が未決定
- **ログインの応答時間**: 未登録のメールでも、ダミーのハッシュ照合（同じコスト係数 12）を行い、応答時間から登録の有無を推測されないようにする

### 2026-10-12 — パスワードは UTF-8 で 72 バイト以内。422 の応答に入力値を含めない
- **判断**
  - 登録と管理者のパスワード変更: 72 バイトを超えたら 422（`password_too_long`）
  - ログインと管理者ログイン: 72 バイトを超える、または UTF-8 にできない文字（孤立サロゲート）を含むパスワードは、未登録・誤りと同じ 401
  - 全 API の 422 の応答から、送信された値（`input`）と `ctx` を除く（`app/validation.py`）
- **理由**: bcrypt は 72 バイトを超えると `ValueError` を出し、500 になっていた（日本語は 1 文字 3 バイトで、25 文字ほどで起きた）。修正前は、422 の応答に平文のパスワードが入っていた
- **影響**: 72 バイト以内の既存のハッシュ・ログインは変わらない。`input` と `ctx` を読むクライアントは無かった

### 2026-10-12 — bcrypt は別スレッドで、同時 4 件まで
- **判断**: 登録・ログイン・管理者ログイン・パスワード変更の bcrypt を `asyncio.to_thread` で別スレッドに出し、`asyncio.Semaphore(4)` で同時 4 件に制限する（`app/auth.py` の `run_blocking_auth`）。ダミー照合も同じ
- **理由**: bcrypt（約 200 ms の CPU 処理）が同期的に走り、取り込みや `/health` を含む、同じプロセスの全要求が止まっていた。ログイン中の別の処理の最大遅延は、216〜228 ms から 12 ms 以下になった
- **影響**: ログインにはレート制限（20 回/分、登録は 10 回/分）があるので、同時 4 件の待ち行列で足りる。管理者ログインを同時に投げた直後に `/health` が 450〜700 ms 遅れることが 1 回あった（原因は未調査）

### 2026-10-12 — 本番は `CHANGE_ME` などの仮の秘密値では起動しない
- **判断**: `ENVIRONMENT=production` で、`JWT_SECRET`（`multi_tenant`）または `INGEST_API_KEY`（それ以外）が、空、または `change-this`・`change_me`・`change-me` で始まる値のときは、起動を拒否する（前方一致）
- **理由**: 以前は `change-this-in-production` との完全一致だけを検査していたため、`.env.cloud.example` の `CHANGE_ME_*` のままでも起動し、公開されている値で JWT が署名された

### 2026-10-04 — Webhook を新設（Phase 1）
- **判断**: イベント `reading.received`（値の受信ごと）と `alarm.triggered`（アラーム発生ごと）を、任意の URL へ JSON で送る
- **理由**: 拡張の主軸（10-01）を実現するための、最小の仕組み
- **意図的に入れなかったもの**: 再試行、送信キュー、署名。必要になった段階で追加する

### 2026-10-04 — プラグイン基盤を廃止（Phase 2）
- **判断**: `app/plugins/`、`/api/plugins`、関連テーブル（`plugins` / `plugin_configs`）を削除する
- **理由**: 10-01 の方針に従い、使われない拡張の仕組みを残さないため。利用例は、サンプルの `reading_logger` だけだった
- **影響（破壊的変更）**: プラグインの設定値は失われる。downgrade はテーブル定義だけを戻し、データは戻らない

### 2026-10-04 — Webhook と Discord の送信先を検証する（SSRF 対策）
- **判断**
  - Webhook: `https` のみ。名前解決した全アドレスが公開 IP のときだけ送る。登録時と送信直前の両方で検証し、リダイレクトは追わない
  - Discord（2026-10-12 に追加）: 通知設定の URL を Webhook と同じ検証に通し、不可なら 422。送信直前にも再検証する。許可リスト（discord.com のみ）にはしない
  - 送信失敗のログには、ホスト名と HTTP 状態（または例外の型名）だけを出す
- **理由**: 利用者が指定した URL にサーバーから送るため、そのままでは社内ネットワークやクラウドのメタデータにアクセスされるおそれがあった。Discord の URL も、以前は内部アドレスを登録でき、失敗のログに秘密の URL が出ていた。許可リストにしないのは、Mattermost など互換サーバーを塞がないため
- **例外**: `WEBHOOK_ALLOW_PRIVATE_NETWORKS=true` で、社内ネットワークを許可できる（自己ホストで社内の自動化基盤を使う場合のみ。既定は禁止）
- **残るリスク**: DNS rebinding（検証と接続の間に DNS の結果が変わる）は、Webhook・Discord とも未対策。接続先の IP を固定すれば防げる

### 2026-10-08 — Webhook の送信は接続を使い回し、同時送信と待ちに上限を置く
- **判断**: 共有のクライアントで接続を使い回す。同時送信は 10 件まで、送信待ちは 1,000 件まで。超えた分は送らずに捨て、件数をログに出す（多くても 1 分に 1 回）
- **理由**: 値の受信ごと・アラームごとに送るため、大量の取り込みや送信先の遅延で、送信のタスク・DNS 検証（スレッド）・接続が際限なく増えていた
- **影響**: 上限を超えると Webhook が届かないことがある（再試行はしない方針のまま）。確実な配送が必要になったら、送信キューと再試行を検討する

## データ移行

SaaS → OSS の移行は、書き出しファイルを介して行う。OSS → SaaS は復旧ツール側で扱う（[バックアップ・復旧](#バックアップ復旧)）。

### 2026-10-04 — 書き出しファイルを介して移行する
- **判断**: 移行元（SaaS）と移行先（OSS）を直接つながず、gzip の JSON Lines の書き出しファイルを介する。書き出しは SaaS の本人だけ、取り込みは OSS のみ
- **理由**: 両方が同じ DB に同時に存在する必要がない。ファイルなら、確認（件数の dry-run）も保管もでき、失敗しても何も残らない
- **影響**: 取り込み API に認証は無い（OSS の前提）。インターネットに直接公開しないこと

### 2026-10-08 — self-hosted にも書き出しを足し、OSS → OSS を完結させる
- **判断**: 書き出しを self-hosted でも使えるようにする（`workspace_id IS NULL` の全データが対象）。OSS → SaaS（ワークスペースを選んでの取り込み）は、このアプリではなく復旧ツール側で扱う
- **理由**: self-hosted の読み取り API はもともと認証が無く、全データが `GET` で読める。書き出しを足しても、読めるものは増えない。一方 OSS → SaaS には、ワークスペースの選択・Free Tier の確認など、認証を前提とする判断が要るため、運用者が操作する復旧ツールに置く
- **影響**: self-hosted どうしの移行・バックアップは、アプリ内の「データ移行」だけで完結する

### 2026-10-04 — ファイルの内容と範囲
- **ID と取り込みキーは保つ**: センサー・ダッシュボードなどの UUID と `ingest_key` は、そのまま移す（デバイス側の設定を変えずに済ませるため）。測定値は主キーが（センサー, 時刻）なので、そのまま移す。同じワークスペースを同じ DB に取り込み直すと、ID が重なって失敗する（何も残らない）。削除済みのダッシュボードも行が残るため、同様に失敗する
- **測定値は差分の配列で書く**: センサーごとに `[値, 前の行からの差分（マイクロ秒）]` の配列にして、5,000 件ずつ 1 行に書く。JSON のキー名と ID を毎行書くと約 14 バイト/件が約 6 バイト/件になる。時刻はマイクロ秒を保つので、往復で完全に戻る
- **通知設定とユーザーは移さない**: ユーザー・リフレッシュトークン・ワークスペースは移さない。通知設定（Discord の URL）は、`with_notifications` を指定したときだけ移し、移行先の ID=1 を上書きする（OSS には認証が無く、通知の URL は移行先で意図して設定するべき値のため）
- **形式の版（2026-10-30 に版 3）**: 機器の表（名前とキーのハッシュ）も、センサーの所属ごと移す。これまでは、機器に所属したセンサーを取り込むと外部キー違反で中止されていた。移行先でも同じキーのまま送れる。取り込みは、版が違うファイル・未知のテーブル・列を拒否する。スキーマの変化への柔軟さは持たせず、版の一致で守る

## バックアップ・復旧

復旧ツールは `tools/recovery/`。2026-10-08 の判断（個別の日付が無い項目）と、2026-10-25〜28 の判断を載せる。

### 本体と別のプログラムにする（2026-10-08）
- **判断**: バックアップの確認・書き戻しは、FactorEye の管理画面ではなく、別のプログラムで行う。Docker があればどこでも動き、設定だけを変える
- **理由**: 不正アクセスでプログラムを壊されたときや、DB が壊れて backend が起動しないときにこそ使う道具だから。インターネットに公開している画面に、「バックアップを読む」「DB に書き込む」機能を置かないため
- **影響**: 画面は Basic 認証で、待ち受けは既定で 127.0.0.1。本番では本体と別の compose で動かし、本体のデプロイの影響を受けない

### 展開は、改ざんされている前提で行う（2026-10-08）
- **判断**: SQL を自分で解釈せず、作業用の Postgres に流し込んでから調べる。流し込みは、psql の `\restrict`・管理者ではないロール・秘密を渡さない環境で行う
- **理由**: sha256 の記録もバックアップと一緒に作り直せるため、検証だけでは改ざんを防げない。QA のレビューで、展開時に任意のコマンドが実行されうることが分かった
- **影響**: 所有者が管理者のロールのバックアップや、行頭にメタコマンドのあるバックアップは展開しない

### 書き戻しは「無い行を足す」だけ（2026-10-08）
- **判断**: 今ある行は変えない・消さない。試行は同じ処理を取り消す。実行は、確認した件数と一致したときだけ、直前に今の DB を控えてから、1 トランザクションで行う
- **理由**: 復旧の操作で、今あるデータを壊さないため。件数の見込みと実際がずれる余地を無くすため
- **影響**: 「バックアップの時点の値に戻す（上書き）」はできない。必要なら、控えと `infra/restore.sh` で丸ごと戻す。測定値は（センサー, 時刻）で同じ行かを判定する（連番の id は持ち込まない）

### OSS 版 ⇄ SaaS 版は、所属を付け替えて書き戻す（2026-10-08）
- **判断**: OSS 版のデータは、SaaS 版の選んだワークスペースへ入れる。SaaS 版のワークスペースは、OSS 版のデータとして入れる。今の DB がどちらの版かは、`TARGET_MODE` で明示する
- **理由**: 運用者から「止めるのではなく、できるように」との指示があった。版をデータの中身で判定すると、空の SaaS 版を OSS 版と取り違える
- **影響**: 書き戻しを使うときは `TARGET_MODE` が必須。付け替えのときは、ユーザー・ワークスペースの行は入れない。2026-10-30 から、OSS 版 → SaaS 版ではセンサーの所属（`device_id`）を外し、OSS 版 → OSS 版では機器（名前とキーのハッシュ）も戻す。キーのハッシュは画面・CSV に出さない

### バックアップは権限 640。本番の外の控えは、本番から消せない形にする（2026-10-08）
- **判断**: バックアップは、所有者とグループだけが読める。S3 は「追加だけ」の鍵とバージョニング、別のマシンは本番から「読むだけ」の鍵（`rrsync -ro`）で取りに行く
- **理由**: バックアップには、利用者のデータとパスワードのハッシュが入る。乗っ取られた本番から、外の控えを消されないようにするため
- **影響**: 復旧ツールのコンテナは、バックアップのグループ（`BACKUP_GID`）で読む

### 2026-10-25 — AWS は「災害時だけ起動する控え」にし、バックアップは Cloudflare R2 に送る
- **判断**: 平常時の本番は Proxmox のまま。AWS には EC2・EBS・パブリック IPv4 を置かず、バックアップを R2 に置き、設定済み EC2 の AMI だけを持つ。災害時に AMI から起動し、R2 から戻す。送信は、既存の `infra/offsite-s3.sh` をそのまま使う（`AWS_ENDPOINT_URL` で R2 に向ける）
- **理由**: 利用者が実質ゼロで、冗長化の費用を払う段階にない。常時稼働の最小構成でも月 $10 前後かかるのに対し、この形なら月 $0〜2。R2 は保管 10GB まで無料で、外向き通信も無料
- **R2 の安全策**: R2 のトークンは追加だけの権限にできないので、バケットのロック（保持期間）で、削除・上書きを防ぐ
- **見送った案**: スポット 1 台＋ EBS ＋ WAL を S3 へ（月 $10〜）、2 台構成（月 $19〜）、Lambda（バックエンドの作りと合わない）、EFS に PostgreSQL を置く案（`hard` マウントの要件、二重起動で破損、遅さ）。利用者が増えたら、スポット 1 台に上げる
- **再検討の目安**: 利用者が付く、または停止を数十分以上許せなくなったとき

### 2026-10-28 — 控え（AWS）が稼いだデータの本番への書き戻しは、管理画面のボタンから復旧ツールを呼ぶ
- **判断**
  - **入口**: 本番アプリの `/admin` に「書き戻し」の区画を置く（一覧 → 試算 → 確認 → 実行 → 結果）。API は `/api/admin/failback/{handoffs,preview,apply}`（管理者トークン、`AUTH_MODE=multi_tenant` のときだけ）
  - **方式**: backend が内部ネットワーク（`factoreye-cloud`）で復旧ツールを HTTP で呼ぶ。backend に本番 DB への新しい書き込みの経路は足さない。認証情報は環境変数（`FAILBACK_RECOVERY_*`）で渡し、コード・ログ・画面に出さない
  - **復旧ツール側**: `HANDOFF_SOURCE`（R2 の `handoff-inc/`）を読み込み元に足し、`GET /api/handoffs` と `POST /api/handoffs/{name}/failback` を追加した。書き戻しは既存の `/merge` と同じ関数（試行 → 件数の再確認 → 直前の控え → 1 トランザクション）を共有する。書き戻しの間 `readings` を `SHARE ROW EXCLUSIVE` でロックする（挿入が待たされる）
  - **守り**: 引き継ぎの sha256・gzip が壊れている、`.sha256` が無い、種類が `reduced` でないときは使わない。スキーマの版（Alembic）が違えば書き込まずに 409。試算の件数と実行の直前の件数が違えば実行しない。展開した引き継ぎは使い終わったら消す
- **理由**: 復旧ツールには、試行・実行・直前の控え・1 トランザクション・件数の再確認がすでにあり、その検証済みの処理を再利用するほうが、backend に同じ書き込みを作るより安全。管理画面から押せると、SSH のトンネルなしで復帰の最後まで行える
- **影響**: 控えの稼働中の既存の行の更新・削除（パスワードの変更など）は戻らない。書き戻した行だけを消す手順は無い（画面と README に明記）。本番の compose で `recovery` が `factoreye-cloud` に入り、`HANDOFF_SOURCE`・`TARGET_WRITE_DATABASE_URL`・`TARGET_MODE=saas` が設定されていることが前提

### 2026-10-28 — Proxmox が消えても、R2 の WAL-G のバックアップから復旧・合流できるようにする
- **判断**
  - **入力**: R2 の `factoreye-db`（WAL-G。ベース ＋ WAL）。復旧ツールのコンテナ内で `backup-fetch LATEST` → `recovery.signal` ＋ `restore_command`（`wal-g wal-fetch`。失敗は 127 で異常終了させ、古い時点での昇格を防ぐ）→ 一時的な PostgreSQL 15（unix ソケットだけ、`archive_mode=off`）で再生 → 昇格後の DB をそのまま merge の入力にする
  - **書き込みは「無い行だけ足す」**: 既存の merge をそのまま使う。複数の元（R2 → 引き継ぎ）は `merge_many` で 1 つのトランザクションにまとめる。UPDATE・DELETE は足さない
  - **読み取りだけ**: 使う WAL-G のコマンドは `backup-list`・`backup-fetch`・`wal-fetch`。鍵は本番の `walg.env` をそのまま使える（ユーザー決定）が、コードは書き込み・削除系を呼ばない。`walg.env` はディレクトリのマウント（`tools/recovery/walg/`）で渡し、読めなくても復旧ツールは起動する（R2 の機能だけ無効）
  - **長い処理**: 復元は復旧ツールの裏のジョブ（画面が 3 秒ごとに状態を見る）。試算・実行は同期で、backend の時間切れは 600 秒
  - **安全**: 復元した PostgreSQL の設定はバックアップのものを使わず最小の自前のものにし、WAL-G の鍵は権限 600 のファイルから読む（作業領域と一緒に消える）。merge の元は読み取りロール（`pg_read_all_data`）で読む。失敗の文から鍵を伏せる。ロックは 10 秒で取れなければ中止
  - **イメージ**: PostgreSQL 15（Debian）と WAL-G v3.0.9（ハッシュ固定）を復旧ツールのイメージに入れる
- **理由**: 毎晩の pg_dump が廃止され、論理ダンプの全体が無い。本番が消えた・不完全なときに、R2 に残る物理バックアップを、既存の検証済みの合流の仕組みに接続するのが最小の変更で安全
- **影響**: 復元には本番の DB と同じ大きさの空きが要る。改ざんされたバックアップの脅威は、論理ダンプの展開ほどは防げない。ログインの状態は戻らない。バックアップの最終時刻より後のデータは R2 に無い

### 2026-10-01 — 自由配置（12 列グリッド）
- **判断**: `react-grid-layout` で、ドラッグ配置と自由なサイズ変更ができる。軸の範囲も後から編集できる
- **理由**: 配置とサイズの制約が強すぎるというフィードバック

### 2026-10-02 — 画面の更新は 5 秒ごとのポーリング
- **判断**: WebSocket は使わない。一覧・最新値・アラームは 5 秒ごと、グラフの直近モードは 30 秒ごとに取り直す
- **理由**: 実装が単純。WebSocket は後のフェーズで検討する方針
- **再検討の目安**: 低遅延が必須の利用者が出たとき

### 2026-10-05 — グラフの時間範囲は Grafana と同じ操作にし、ダッシュボード単位で持つ
- **判断**: グラフは、過去への移動・現在への復帰・期間の変更（プリセットと任意の期間）・拡大縮小・ドラッグでの選択ができる。時間範囲はダッシュボードに 1 つだけ持ち、SensorGraph と MultiSensorComparison が同じ範囲に従う。範囲は URL に保持し、ダッシュボードには保存しない
- **理由**: センサーの過去の変化を、前後の時間も含めて追えるようにするため。範囲をウィジェットごとにすると、比較グラフの時間軸がずれる
- **影響**: 長い期間の表示のため、間引き API（`/api/sensors/{id}/readings/downsampled`）を追加した。SaaS は 14 日まで。範囲は保存しないので、開き直すと既定の「直近 1 時間」に戻る

### 2026-10-12 — 画面ごとに遅延読み込みし、デプロイ後のチャンク失敗は 1 回だけ再読み込みする
- **判断**
  - **遅延読み込みする**: ダッシュボード（`DashboardView`）・設定・セットアップガイド・管理者画面（`AdminApp`）・規約（`LegalPage`）と、recharts を使うウィジェット 3 種（`SensorGraph`・`MultiSensorComparison`・`StatValue`）を `React.lazy` で分ける。ログイン画面・ダッシュボード一覧・小さなウィジェットは、初期表示に要る、または分けても往復が増えるだけなので分けない
  - **vendor を分ける**: `manualChunks` で、`vendor-react` と `vendor-charts`（recharts と d3 など）に分ける
  - **キャッシュ**: `index.html` は `Cache-Control: no-cache`（nginx.conf）
  - **チャンクの読み込み失敗**: 動的 import が失敗したら、`lib/lazyWithRetry.ts` が 1 回だけ自動で再読み込みする（`sessionStorage` の印。成功したら消す）。それでも失敗したら、`ChunkErrorBoundary` が再読み込みの案内を出す（チャンク以外のエラーは上へ投げ直す）
- **理由**: 単一チャンク 785 KB（gzip 232 KB）が、初期ロード 203 KB（gzip 65 KB）になった。recharts（約 419 KB）は、グラフ系のウィジェットが出るときだけ読み込まれ、アプリの更新後も再取得されない。デプロイのたびにチャンクのハッシュが変わり、古い `index.html` を持つブラウザは消えたチャンクを要求して失敗するため、`index.html` をキャッシュさせず、残った失敗は再読み込みで切り替える
- **影響**: 画面を初めて開くときに、小さな読み込み待ちが 1 回入る（以後はキャッシュ）。新しい画面を足すときは、`lazyNamed` で分け、`Suspense` と `ChunkErrorBoundary` で囲む

## 性能

### 2026-10-05 — 一覧の応答は ORM を通さず、JSON を 1 回だけ作る
- **判断**: 測定値・アラーム・センサーの一覧は、必要な列だけを読み、Pydantic のモデルから JSON を 1 回だけ作って返す（`app/api/responses.py`）。OpenAPI の定義は `response_model` で残す
- **理由**: py-spy の計測で、CPU の大半は ORM のオブジェクト生成と、FastAPI の二重の変換（モデル → dict → 検証 → JSON）だった
- **影響**: 応答の形（camelCase の項目）は変わらない。列を追加するときは、一覧の列の定義（`_LIST_COLUMNS` など）にも追加する

### 2026-10-05 — アラーム一覧はページングし、警告の表示は 100 件まで
- **判断**: `GET /api/alarms` に `limit`（1〜500、省略時は全件）と `offset` を追加する。警告の表示は、発生中と確認済みを、それぞれ新しい順に 100 件まで取る
- **理由**: 全件の応答は約 210KB・約 0.4 秒で、取り直しのたびに CPU を使っていた
- **影響**: API の既定の動きは従来どおり（全件）。`total` は、ページで区切る前の件数。確認済みが 100 件を超えると、古いものは警告の表示には出ない（設定画面では見られる）

### 2026-10-05 — センサー一覧は ETag で 304 を返し、版ごとに JSON を保持する
- **判断**: 版（ETag）は、件数と最終更新時刻から作る。`If-None-Match` が一致すれば 304（本体なし）。完成した JSON を、版ごとにプロセス内に保持する（上限 32 件）
- **理由**: 画面と負荷テストが数秒ごとに全件を取り直し、300 件分の変換が CPU の大部分を使っていた
- **影響**: センサーを変更するときは、必ず件数か `updated_at` を変えること。変わらないと、古い一覧が返る（architecture.md §4.1）。キャッシュはプロセスごと

### 2026-10-12 — flush は読み込みを減らし、稼働ステータスは最新の 1 件だけ取る
- **判断**
  - 取り込みバッファの flush（`flush_once`）は、センサーを 1 回の `select` で読み、結果をアラームの判定と通知に引数で渡す（以前は 3 回）
  - commit 後の Webhook 配信には、commit 前に作ったプレーンな値を渡す（commit 後の ORM オブジェクトへのアクセスは、非同期では例外になる）
  - 稼働ステータスのウィジェットは、測定値を 500 件ではなく最新の 1 件だけ取る
- **理由**: 稼働ステータスは、5 秒ごとに約 60KB を取りながら、使うのは最新の 1 件（約 0.12KB）だけだった。flush の短縮は小さい（クエリが 10 本から 8 本）
- **影響**: commit 後にセンサーが削除された場合、以前は未登録扱いになり、self-hosted の購読へ誤って送り得た。今は commit 前の値で送る

### 2026-10-12 — 期限切れの `refresh_tokens` を毎日削除する
- **判断**: 毎日 UTC 03:00 の `purge_loop` で、`expires_at` が 7 日より前の行を、1,000 件ずつ別トランザクションで削除する。期限内の行は、失効済みでも残す
- **理由**: ログイン・更新のたびに 1 行増え、削除する処理が無かった。失効済みトークンの再利用を検知する仕組みは無いので、行を消しても安全性は変わらない。7 日は障害調査用の余裕
- **影響**: `expires_at` に索引が無く、削除は全件走査になる（数万行までは問題ない）。増えたら索引を足す

## 配布（Docker）

イメージの大きさは、すべて実測（Mac arm64）。

### 2026-11-03 — OSS 版は「1 コマンドで入る」配布物（`install/`）にする。ルートの compose は変えない
- **判断**: `curl … | sudo bash` の `install/install.sh` が、Docker の導入・乱数の鍵つき `config/.env` の生成・公開済みイメージの取得・起動までを行う。イメージは GHCR（amd64 + arm64）にタグで公開する。配布用の compose は `install/` に独立させ、ルートの `docker-compose.yml`（ソースからビルド）は変えない
- **理由**: 公開にあたり、`git clone` と `docker compose up --build`、`VITE_API_URL` に IP を書いて再ビルドする手順、既定の鍵のままでも起動できること、が導入の壁だった。ルートの compose は Raspberry Pi の運用・E2E・`infra/` のスクリプトが使っており、書き換えると既存の運用が黙って別物になる
- **影響**: 画面と API の入口を 1 ポートにした（frontend の nginx が `/api` を転送し、`VITE_API_URL` は空 = 同じオリジン）。レート制限は `CF-Connecting-IP`（接続元）を使うため、nginx が接続元を付け直す。frontend の Dockerfile のビルド段は `$BUILDPLATFORM` で動かし、arm64 向けでも npm を QEMU で動かさない

### 2026-11-03 — 設定は `config/.env` の 1 ファイル。画面から変えられ、直接編集もできる
- **判断**: 取り込みの鍵・認証・自動登録・レート制限などの設定を、`config/.env` の 1 ファイルに集約する。画面（設定 → API・取り込み）は、管理パスワードで解錠して変更し、保存すると `.env` を書き換えて backend が自分を再起動する。直接編集したときは、パスワードなしの「ファイルの内容を反映」で取り込む（起動後に書き換わっているときだけ受け付け、検査に通らなければ再起動しない）。Discord・Webhook の送信先・機器キー・センサーは、画面で増減するものなので DB のまま
- **理由**: 設定の置き場が 2 つあると、どちらが正か分からなくなる。画面からも直接も変えられることが要件。再起動で反映するのは、起動時に 1 回読む既存の設定の仕組みを変えないため
- **影響**: backend は設定を環境変数でなく `.env` から直接読む（環境変数は `.env` より優先されるため）。`JWT_SECRET`・DB パスワード・`DATABASE_URL` は画面から変えられない。管理パスワードのハッシュ（`$` を含む）は単一引用符で囲む。画面で保存する前の内容は `config/.env.bak` に残し、`./factoreye.sh restore-env` で戻せる

### 2026-11-03 — `.env` はディレクトリごとマウントする（ファイル 1 つのマウントは使わない）
- **判断**: `./config`（`.env` と `.env.bak`）を backend にマウントする。compose の変数も `--env-file config/.env` で同じファイルから読む
- **理由**: ファイル 1 つのバインドマウントは、ホストで `sed -i`・vim のように新しいファイルに置き換えて保存すると、コンテナが古い実体を見続けた（反映ボタンが「変更なし」と返し、500 も出た。実機相当の確認で発見）

## 運用上の注意

これまでの作業で起きた問題から、次の点を守ること。

**テスト・環境**
- **テスト DB を分ける**: backend のテストは、接続先のすべてのテーブルを作り直して削除する。開発用・本番用の DB に向けるとデータが消える（実際に起きた）。テスト専用の DB を指定すること
- **フレッシュな環境で一度は通す**: ローカルの使い回しの DB では、マイグレーションの未適用やヘルスチェックの競合が見えない。リリース前に、CI のような空の環境での起動を一度行う（実際に、空の DB で起動できない不具合が見つかった）
- **`docker compose down -v` は慎重に**: `-v` はボリューム（DB のデータ）も削除する。実行前に `docker compose ps` で、自分が起動したコンテナか確認する

**マイグレーション・データ削除**
- **マイグレーションは往復を確認する**: `alembic downgrade` と `upgrade` を通してから取り込む
- **Enum 型のマイグレーション**: `op.create_table` は Enum 型を自動で作るので、事前の `create()` は重複エラーになる。`add_column` は事前の作成が要る
- **バックアップを取ってから破壊的な操作をする**: テーブル削除・マイグレーションの downgrade の前に、`infra/backup.sh` で取る
- **利用者データは外部キーの順に消す**: `refresh_tokens` → `widgets`（`dashboards` を参照）→ `workspaces`（連動して `sensors`・測定値・アラーム・ダッシュボードが消える）→ `users`。順番を誤ると途中で失敗する（トランザクションで囲み、件数を確かめてから確定する）
- **消した後は領域を戻す**: DELETE では DB の使用量はすぐには減らない。表が空になったら `VACUUM FULL <表名>` で OS に返す

**計測・負荷テスト**
- **性能の計測は、アプリを変えずに行う**: `docker run --pid=container:<backend> --cap-add SYS_PTRACE` で、別のコンテナから py-spy を実行する。関数ごとの配分は近似
- **負荷テストの前に Webhook の登録を確認する**: 閾値を超える値を多く送るため、アラームごとに Webhook が送られ、CPU を使う（実際に起きた）。不要なものは消す

**実装**
- **センサーを更新したら `updated_at` を更新する**: センサー一覧の版（ETag）は、件数と `updated_at` で判定している（architecture.md §4.1）
