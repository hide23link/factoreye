# 設計判断の記録

主要な設計判断と、その理由です。仕様は [`architecture.md`](architecture.md)、変更履歴は [`CHANGELOG.md`](../CHANGELOG.md) にあります。

**書き方**: 各項目は「判断 / 理由 / 影響」。判断が覆ったら、古い項目を消して新しい判断を書く（経緯は git の履歴に残る）。

## 製品方針

### 2026-10-01 — 拡張は Python プラグインではなく Webhook で行う
- **判断**: 業種別の拡張は Webhook（イベントを JSON で送る）とルール設定で実現する
- **理由**: 対象は技術者でない工場スタッフ。プラグインは Python を書く必要があり、安全に配布する仕組みも無い。Webhook なら Zapier・Make・n8n などでコード無しに連携できる
- **影響**: 2026-10-04 にプラグイン基盤を廃止した（破壊的変更。設定値は失われた）

### 2026-10-02 — 通知は Discord Webhook のみ。通知設定は DB に持つ
- **判断**: 基本機能の通知は Discord だけ（SMTP は削除）。URL・有効/無効・再通知の設定は `.env` でなく DB に保存し、設定画面から変える
- **影響**: 他サービスへの通知は Webhook で行う

### 2026-10-02 — 生産数は「時間・日・目標達成率」。OEE は採用しない
- **理由**: OEE には停止理由の記録とシフトのカレンダーが要る。複雑な生産管理は作らないという方針に反する

## データモデル

### 2026-10-02 — アラームは 2 段階、しきい値は 4 項目、解除には不感帯を置く
- **判断**: 重要度は軽故障（warning）と重故障（critical）。しきい値は「上限・下限」×「軽・重」の 4 項目。発生は閾値を超えた時点、解除は閾値から不感帯の幅だけ戻ったとき（ヒステリシス）
- **理由**: 「すぐ止める」と「様子を見る」で通知先・通知音を分けたい。不感帯がないと、閾値付近の揺れで発生と解除が繰り返され、通知が溢れる
- **影響**: 重要度が変わったら既存の行を更新する（履歴が増えすぎないため）。3 段階以上が必要になったら再検討する

### 2026-10-02 — センサーは物理削除、ダッシュボードは論理削除
- **理由**: センサーを論理削除にすると、削除済みと同名のセンサーを登録できず利用者が混乱した。ダッシュボードには同名の問題が無い
- **影響**: センサーを消すとアラーム履歴も消える。監査用に残す要件が出たら再検討する
- **注意**: DB の CASCADE だけでは足りず、SQLAlchemy が子の行を読んで外部キーを NULL にしようとする。`passive_deletes` で DB 側の連動削除に任せている

### 2026-10-25 — readings の主キーを (sensor_id, recorded_at) にする
- **判断**: 連番の `id` を廃止し、主キーを `(sensor_id, recorded_at)` にする。索引は主キーに含まれるので別に持たない
- **理由**: 実測（PostgreSQL 15、10 センサー・5 秒間隔、200 万行）で 1 行 161 B → 101 B（約 4 割減）、500 万行の書き込みは 8.3 秒 → 5.6 秒。検索は同等（差は 1 割以内）。拡張は不要で、`pg_dump` と復旧の手順は変わらない。測定値がまだ少ないうちに行った
- **取り込みの扱い**: 1 回の送信内の値は、センサーごとに「前に割り当てた最後の時刻」より必ず 1 マイクロ秒以上進めて割り当てる（送信どうしも重ならず、時計が戻っても重ならない）。それでも重なる場合（複数プロセス、再起動直後の時計の戻り、commit の応答が失われた後の再試行など）は `ON CONFLICT DO NOTHING` で書かずに続け、書けなかった件数を警告ログに出す。INSERT は 5,000 行ずつに区切る（asyncpg の 1 文のパラメータは 32,767 個まで）
- **移行**: 旧データは 1 行も捨てない。同じ時刻の旧データは、1 行を元の時刻に、残りを空いている時刻まで 1 マイクロ秒ずつずらして入れる。最後に件数を比べ、合わなければ移行全体を取り消す。実測: 500 万行で 13 秒、766 MB → 481 MB。適用はアプリを止めてから行い、readings の 2 倍程度の空きを要する（`infra/check-migration-space.sh` で確かめる）
- **影響**: スキーマの版が変わるため、適用前のバックアップは書き戻しに使えない（同じ版どうしに限る）。API の `id` は応答から消えた（互換性なし）
- **見送った案**: センサー番号を `smallint`・値を `float4` にする案（さらに 17% 減だが、対応表と精度の確認が要る）、BRIN だけにする案（速度は未測定）、1 時間 1 行の配列にする案（約 95% 減だが、取り込み・アラーム・間引き・復旧ツールを作り直す）

### 2026-10-02 — 時系列の DB は TimescaleDB を採らない
- **判断**: 複合インデックス `(sensor_id, recorded_at)` で対応する
- **再検討の目安**: 測定値が 1,000 万行を超える、またはダッシュボードのクエリが 500 ms を超える
- **理由（2026-10-25 の実測）**: 圧縮は効果が大きい（161 B/行 → 約 12 B/行）。ただし、①圧縮済みの塊への `DELETE`/`UPDATE` は既定の上限（10 万行）で失敗する、②圧縮済みへの `INSERT` は素の 1/18 の速さ（書き戻しが遅い）、③ダンプを拡張なしの PostgreSQL に戻せない（復旧と OSS 版の行き来に影響）、④主キーに時刻が要る。拡張に依存しない方法を先に採ったので見送りを続ける

### 2026-10-12 — 未使用の `widget_configs` テーブルを削除
- **理由**: ウィジェットの設定は `widgets.config` に持ち、本番・OSS 版とも 0 件だった

### 2026-10-12 — メールは小文字にそろえ、`lower(email)` の一意インデックスで重複を防ぐ
- **判断**: 登録・ログイン・管理者のメール修正では前後の空白を除いて小文字にし、比較は `lower(email)`。同時登録の一意制約違反は 500 でなく 409
- **理由**: 大文字小文字だけが違うメールが別のアカウントになっていた。`lower()` の比較を索引で速くするため、式の索引を使う（5,000 行で Index Scan のコスト 8.30、Seq Scan は 122）
- **影響**: 復旧ツールのマージで、大文字小文字だけが違うメールが両側にあると失敗する。登録時の「既に登録されている」応答で登録の有無が分かる点は、方針が未決定

## 技術選定

### 2026-10-02 — DB は PostgreSQL 15 のみ
- **判断**: 開発・テスト・本番のすべてで PostgreSQL 15（テストも PostgreSQL に接続する）
- **理由**: 当初は開発・テストに SQLite を想定したが、全環境を揃えた

### 2026-10-02 — 画面の更新は 5 秒ごとのポーリング
- **判断**: WebSocket は使わない。一覧・最新値・アラームは 5 秒、グラフの直近モードは 30 秒
- **理由**: 実装が単純。低遅延が必須の利用者が出たら再検討する

### 2026-10-06 — frontend は nginx で静的配信、backend は多段ビルドにする
- **判断**: frontend の実行段は `nginx:alpine` にビルド済みの `dist/` だけを置く。backend は実行段に venv と本体だけ入れ、開発用の依存（`requirements-dev.txt`）を分ける
- **理由**: `vite preview` と開発用の依存が本番イメージに残っていた。イメージは frontend 428 → 63 MB、backend 421 → 283 MB
- **影響**: API の URL はビルド時の `VITE_API_URL` で決まる（変えるには再ビルド）
- **見送り**: `python:3.12-alpine`（177 MB まで減るが、musl 上の性能と挙動を確認していない）

### 2026-10-12 — 復旧ツールのイメージから JIT と Perl を外す
- **理由**: 512 MB → 299 MB。作業用の DB は initdb・pg_ctl・psql・pg_dump を直接呼ぶだけなので、JIT と Perl は使わない
- **影響**: イメージは apt の整合が崩れた状態（`dpkg --purge --force-depends`）。イメージの中で `apt` は使わない

## 認証・SaaS

### 2026-10-03 — SaaS はマルチテナント（共有 DB + `workspace_id`）
- **判断**: テナントごとに DB を分けず、同じ DB の中でワークスペース単位に分離する。`workspace_id` が NULL のデータが self-hosted

### 2026-10-03 — Free Tier の制限
- **判断**: センサーは 10 個まで（超過は 402）。測定値は 14 日で削除（SaaS のセンサーだけ。当初 90 日、2026-10-28 に 14 日へ変更）
- **理由**: 超過分は将来の有料プランで扱う方針。14 日は、DR のバックアップ量と復旧時間を小さくするため（500 センサー × 5 秒で DB 約 100 GB → 約 12 GB、初回のベース送信が 8〜22 時間 → 1〜3 時間）
- **影響**: 次の 03:00（UTC）の削除で、14 日より古い測定値は戻せずに消える。画面の期間の最長も 14 日

### 2026-10-03 — 管理者アカウントは DB に入れない
- **判断**: 管理者はサーバー上のテキストファイル（bcrypt ハッシュ）で管理する
- **理由**: 運用者だけが使うアカウントを、利用者のデータと分けるため
- **影響**: ファイルは DB のバックアップに含まれない。別に保管する

### 2026-10-04 — センサー名はワークスペース内で一意、取り込みキーは全体で一意
- **理由**: 名前を全体で一意にすると、別のワークスペースが同じ名前を使えなかった。取り込み API はキーだけでセンサーを特定するので、キーは全体で一意である必要がある
- **影響**: 他のワークスペースのキーと衝突すると 409（キーが使われていることが分かる。存在の確認になる）

### 2026-10-04 — 通知設定はワークスペースごとに 1 行
- **理由**: ID=1 に固定していたため、SaaS のアラームが他のワークスペースの設定で送られるおそれがあった。設定が無いワークスペースは Discord 通知をしない

### 2026-10-04 — リフレッシュトークンは使うたびにローテーション
- **理由**: 盗まれたトークンの再利用を見つけやすくするため
- **影響**: 失効済みトークンの再利用を検知する仕組みは無く、401 を返すだけ

### 2026-10-12 — パスワードは UTF-8 で 72 バイト以内。422 の応答に入力値を含めない
- **判断**: 登録と管理者のパスワード変更は、72 バイトを超えたら 422（`password_too_long`）。ログインは、超過や UTF-8 にできない文字を含むものを未登録・誤りと同じ 401 にする。全 API の 422 から送信値（`input`）と `ctx` を除く
- **理由**: bcrypt は 72 バイトを超えると 500 になっていた（日本語は約 25 文字で起きた）。422 の応答に平文のパスワードが入っていた
- **影響**: 既存のハッシュとログインは変わらない

### 2026-10-12 — bcrypt は別スレッドで、同時 4 件まで
- **判断**: bcrypt（約 200 ms の CPU 処理）を `asyncio.to_thread` に出し、`Semaphore(4)` で同時 4 件に制限する。ダミー照合も同じ
- **理由**: 同期的に走り、同じプロセスの取り込みや `/health` を含む全要求が止まっていた。ログイン中の別の処理の最大遅延は 216〜228 ms から 12 ms 以下になった

### 2026-10-12 — 本番は既定の秘密値のままでは起動しない
- **判断**: `ENVIRONMENT=production` で、`JWT_SECRET` または `INGEST_API_KEY` が空、または `change-this`・`change_me`・`change-me` で始まるときは起動を拒否する（前方一致）
- **理由**: 完全一致だけを見ていたため、`CHANGE_ME_*` のひな形のままでも起動し、公開されている値で JWT が署名された

### 2026-10-18 — self-hosted の取り込みは、設定でキーなしにできる（`INGEST_AUTH=off`）
- **判断**: `INGEST_AUTH=off` のとき、`X-API-Key` を確かめず、`ingestKey` だけでセンサーを識別する。`INGEST_API_KEY` は使わないので、本番の既定値の検査もしない
- **理由**: 機器に長い共有キーを入れたくない。キーは全機器に同じものを配るため、1 台から漏れると全台に影響する。空のキーを「キーなし」と読み替える案は、設定の入れ忘れで意図せず開くので避け、明示の設定にした
- **影響**: `ingestKey` を知っていれば誰でも書ける。取り込みの口は LAN などに限定する（`infra/lan-ingest/`）

### 2026-10-19 — self-hosted は未登録の ingestKey のセンサーを自動で作れる（`INGEST_AUTO_CREATE=on`）。SaaS は対象外
- **判断**: 既定は off。on のとき、未登録のキーでセンサーを作る条件と上限は `architecture.md` §5 のとおり
- **理由**: 機器を増やすたびに画面で登録するのが手間。SaaS は取り込みが `ingestKey` だけでワークスペースを決めるので、未登録のキーからは作る先が決まらない（使うなら、ワークスペース単位の機器登録キーという別の設計が要る）
- **影響**: on の間は、打ち間違いの ID でもセンサーが増える（上限で止まる）。`INGEST_AUTH=off` と組むと、LAN の誰でも上限まで作れる

## Webhook・通知

### 2026-10-04 — Webhook と Discord の送信先を検証する（SSRF 対策）
- **判断**: `https` のみ、名前解決した全アドレスが公開 IP のときだけ送る。登録時と送信直前に検証し、リダイレクトは追わない。Discord の URL も同じ検証を通す（許可リストにはしない。Mattermost など互換サーバーを塞がないため）。送信失敗のログにはホスト名と理由だけを出す
- **理由**: 利用者が指定した URL にサーバーから送るため、社内ネットワークやクラウドのメタデータにアクセスされるおそれがあった。Discord の URL は、トークンを含む秘密がログに出ていた
- **例外**: `WEBHOOK_ALLOW_PRIVATE_NETWORKS=true`（自己ホストで社内の自動化基盤を使う場合のみ）
- **残るリスク**: DNS rebinding。接続先の IP を固定すれば防げる

### 2026-10-08 — Webhook の送信は接続を使い回し、同時送信と待ちに上限を置く
- **判断**: 同時送信 10 件、送信待ち 1,000 件まで。超えた分は送らずに捨てる
- **理由**: 値の受信ごと・アラームごとに送るため、大量の取り込みや送信先の遅延で、タスク・接続・DNS 検証が際限なく増えていた
- **影響**: 上限を超えると届かないことがある（再試行はしない方針のまま）

### 2026-10-12 — デバイスクライアントは、エラーの種類で再送を分ける
- **判断**: 仕様は `architecture.md` §9 のとおり（通信エラー・5xx・408・429 は再送、401・403・404 は保持して再送、400・422 は捨てる、NaN は送る前に捨てる）
- **理由**: 以前は 4xx も再送していたため、NaN を 1 件送ると 400 が続き、そのセンサーが最大約 100 件の間、送れなくなった

## 管理画面

### 2026-10-05 — 取り込みのレート制限は、管理画面から期限付きで解除できる
- **判断**: 既定 60 分・最長 240 分。期限を過ぎると自動で既定に戻る。状態はメモリだけに持つ
- **理由**: 切り替えのたびに環境変数を変えて再起動する手間をなくすため。期限は、解除したまま戻し忘れる事故を防ぐため
- **影響**: 再起動すると既定に戻る。環境変数が `off` のときは画面から変えられない。単一インスタンス前提

## データ移行

### 2026-10-04 — 書き出しファイルを介して移行する（SaaS → OSS）
- **判断**: 移行元と移行先を直接つながず、gzip の JSON Lines の書き出しファイルを介する。取り込みは OSS のみ
- **理由**: 両方が同時に存在する必要がない。ファイルなら件数の dry-run と保管ができ、失敗しても何も残らない
- **影響**: 取り込みに認証は無い（OSS の前提）。インターネットに直接公開しない

### 2026-10-08 — self-hosted にも書き出しを足し、OSS → OSS をアプリ内で完結させる。OSS → SaaS は復旧ツールで扱う
- **理由**: self-hosted の読み取り API は元々認証が無く、全データが読める。書き出しを足しても新たな漏えいにはならない。一方 OSS → SaaS には、ワークスペースの選択や Free Tier の確認など認証を前提とする判断が要る。運用者が操作する復旧ツールに置く

### 2026-10-04 — 測定値は差分の配列で書き、ID と取り込みキーは保つ
- **判断**: 測定値は `[値, 前の行からの差分（マイクロ秒）]` の配列で、5,000 件ずつ 1 行に書く（形式の版 2）。センサー・ダッシュボードの UUID と `ingest_key` はそのまま移す。測定値の ID は振り直す
- **理由**: JSON のキー名と ID を毎行書くと約 14 バイト/件。配列と差分にすると約 6 バイト/件で、約 6 割減る。デバイス側の設定（取り込みキー）を変えずに済ませるため
- **影響**: 同じワークスペースを同じ DB に取り込み直すと ID が重なって失敗する（何も残らない）

### 2026-10-04 — ユーザーと通知設定は既定では移さない
- **判断**: ユーザー・リフレッシュトークン・ワークスペースは移さない。通知設定（Discord の URL）は `with_notifications` を指定したときだけ、移行先の ID=1 を上書きする
- **理由**: OSS には認証が無い。通知の URL は移行先で意図して設定するべき値

## バックアップ・復旧

復旧ツールは `tools/recovery/`、バックアップの運用は `infra/README.md` にある。

### 2026-10-08 — 復旧ツールは本体と別のプログラムにする
- **判断**: バックアップの確認と書き戻しは、FactorEye の画面ではなく別のプログラムで行う。Docker があればどこでも動き、設定だけを変える
- **理由**: 不正アクセスでプログラムを壊されたとき、DB が壊れて backend が起動しないときにこそ使う道具だから。インターネットに公開している画面に、バックアップを読む・DB に書く機能を置かないため
- **影響**: 画面は Basic 認証で、待ち受けは既定で 127.0.0.1

### 2026-10-08 — バックアップは改ざんされている前提で展開する
- **判断**: SQL を自分で解釈せず、作業用の Postgres に流し込んでから調べる。流し込みは psql のメタコマンドを止め、管理者ではないロールで、秘密の環境変数を渡さずに行う
- **理由**: 乗っ取られた本番では、バックアップと `.sha256` を一緒に作り直せるため、sha256 の一致だけでは改ざんを防げない
- **影響**: 所有者が管理者のロールや、行頭にメタコマンドのあるバックアップは展開しない

### 2026-10-08 — 書き戻しは「無い行を足す」だけ
- **判断**: 今ある行は変えない・消さない。試行は同じ処理を取り消す。実行は、確認した件数と一致したときだけ、直前に今の DB を控えてから、1 トランザクションで行う
- **理由**: 復旧の操作で、今あるデータを壊さないため
- **影響**: 「バックアップの時点の値に戻す（上書き）」はできない。必要なら `infra/restore.sh` で丸ごと戻す

### 2026-10-08 — 測定値は（センサー, 時刻）で同一かを判定する
- **理由**: DB を作り直すと連番が最初から振られ、バックアップの id と別の行の id が重なるため

### 2026-10-08 — OSS 版 ⇄ SaaS 版は、所属を付け替えて書き戻す
- **判断**: 今の DB がどちらの版かは `TARGET_MODE` で明示する（データの中身から判断しない）
- **理由**: 空の SaaS 版は OSS 版と取り違えられるため。運用者から「止めるのではなく、できるように」との指示があった

### 2026-10-08 — バックアップは権限 640。本番の外の控えは本番から消せない形にする
- **判断**: S3 は「追加だけ」の鍵とバージョニング、別のマシンは本番から読むだけの鍵（`rrsync -ro`）で取りに行く
- **理由**: バックアップには利用者のデータとパスワードのハッシュが入る。乗っ取られた本番から、外の控えを消されないようにするため

### 2026-10-25 — AWS は「災害時だけ起動する控え」にし、バックアップは Cloudflare R2 に送る
- **判断**: 平常時の本番は Proxmox のまま。AWS には EC2・EBS・パブリック IPv4 を置かず、バックアップを R2 に置き、設定済み EC2 の AMI だけを持つ。災害時に AMI から起動し、R2 から戻す
- **理由**: 利用者が実質ゼロで、冗長化の費用を払う段階にない。常時稼働の最小構成は月 $10 前後、この形なら月 $0〜2。R2 は保管 10 GB まで無料で、外向き通信も無料
- **R2 の安全策**: R2 のトークンは「追加だけ」にできないので、バケットのロックで削除・上書きを防ぐ
- **見送った案**: スポット 1 台 + EBS + WAL を S3（月 $10〜、数分で復旧）、2 台構成の DB 複製（月 $19〜）、Lambda（バックエンドの作りと合わない）、EFS 上の PostgreSQL（要件と速度の面で不可）
- **再検討の目安**: 利用者が付く、または停止を数十分以上許せなくなったとき
- **未確認**: AMI からの復旧の訓練、IPv6 のみの VPC（GitHub は IPv4 専用なので、イメージは CI でビルドして配る案が有力）

### 2026-10-28 — 控え（AWS）が稼いだデータは、管理画面のボタンから復旧ツールを呼んで本番へ書き戻す
- **判断**: 本番アプリの `/admin` に「書き戻し」を置き、backend が内部ネットワークで復旧ツールを呼ぶ。backend に本番 DB への新しい書き込みの経路は足さない
- **理由**: 復旧ツールには、試行・実行・直前の控え・1 トランザクション・件数の再確認がすでにあり、検証済みの処理を再利用するほうが、backend に同じ書き込みを作るより安全。SSH のトンネルを使わずに、復帰の手順の最後まで行える
- **影響**: 控えの稼働中の既存行の更新・削除は戻らない。起点より前に発生して起点以降に解除されたアラームの変化も戻らない。書き戻しの間は `readings` をロックする

### 2026-10-28 — Proxmox が消えても、R2 の WAL-G のバックアップから復旧・合流できるようにする
- **判断**: R2 の `factoreye-db`（WAL-G）のベース ＋ WAL を、復旧ツールの裏のジョブで一時的な PostgreSQL に再生し、昇格後の DB を既存の書き戻しの入力にする。使う WAL-G のコマンドは読み取りだけ
- **理由**: 毎晩の pg_dump が廃止され、論理ダンプの全体が無い。既存の検証済みの合流の仕組みに接続するのが最小の変更で安全
- **影響**: 復元には本番と同じ大きさの空きが要る。改ざんされたバックアップの脅威は、論理ダンプの展開ほどは防げない（鍵のファイルは同じユーザーから読める）。バックアップの最終時刻より後のデータは R2 に無い
- **未確認**: 実際の R2 での試験（現時点では WAL-G のファイルの置き場での試験のみ）。空の本番へ戻す物理の復元スクリプトは作らない（管理画面で戻せるため。2026-10-29 の判断）

## 性能

### 2026-10-05 — 一覧の応答は ORM を通さず、JSON を 1 回だけ作る
- **理由**: 計測で、CPU の大半は ORM のオブジェクト生成と、FastAPI の二重の変換だった
- **影響**: 応答の形は変わらない。列を追加するときは一覧の列の定義にも追加する

### 2026-10-05 — アラーム一覧はページングし、警告の表示は 100 件まで
- **理由**: 全件の応答は約 210 KB・約 0.4 秒で、取り直しのたびに CPU を使っていた
- **影響**: 既定の動きは全件のまま。確認済みが 100 件を超えると、古いものは警告の表示には出ない（設定画面では見られる）

### 2026-10-05 — センサー一覧は ETag で 304 を返し、版ごとに JSON を保持する
- **理由**: 画面と負荷テストが数秒ごとに全件を取り直し、300 件分の変換が CPU の大部分を使っていた
- **影響**: センサーを変更するときは、必ず件数か `updated_at` を変えること（architecture.md §4.1）

### 2026-10-12 — flush の読み込みを減らし、稼働ステータスは最新の 1 件だけ取る
- **判断**: flush はセンサーを 1 回の select で読み、結果を通知と判定に渡す。commit 後の Webhook には commit 前に作った値を渡す（commit 後の ORM へのアクセスは非同期では例外になる）。稼働ステータスは最新の 1 件だけ取る
- **理由**: 稼働ステータスは 5 秒ごとに約 60 KB を取りながら、使うのは最新の 1 件（約 0.12 KB）だけだった
- **影響**: commit 後にセンサーが削除されていても、以前は誤って購読先へ送り得た。今は commit 前の値で送る

### 2026-10-12 — 期限切れの `refresh_tokens` を毎日削除する
- **判断**: 毎日 03:00 UTC に、`expires_at` が 7 日より前の行を 1,000 件ずつ削除する。期限内の行は失効済みでも残す
- **理由**: ログインのたびに 1 行増え、削除する処理が無かった。7 日は障害調査用の余裕
- **影響**: `expires_at` に索引が無い（数万行までは問題ない。増えたら索引を足す）

## フロントエンド

### 2026-10-12 — 画面ごとに遅延読み込みし、デプロイ後のチャンク失敗は 1 回だけ再読み込みする
- **判断**: ダッシュボード・設定・セットアップ・管理者画面・規約と、recharts を使うウィジェットを `React.lazy` で分ける。vendor は react と charts に分ける。`index.html` は `no-cache`。チャンクの読み込みに失敗したら、タブごとに 1 回だけ自動で再読み込みし、それでも失敗したら案内を出す
- **理由**: 初期ロードが 785 KB（gzip 232 KB）から 203 KB（gzip 65 KB）になった。デプロイのたびにチャンクのハッシュが変わるため、古い `index.html` のブラウザは消えたチャンクを要求して失敗する
- **影響**: 新しい画面を足すときは `lazyNamed` で分け、`Suspense` と `ChunkErrorBoundary` で囲む

## 運用上の注意

- **テストの DB を分ける**: backend のテストは接続先のテーブルを作り直して消す。開発用・本番用の DB に向けるとデータが消える（実際に起きた）
- **空の環境で一度は通す**: ローカルの使い回しの DB では、マイグレーションの未適用が見えない。リリース前に空の環境で起動する（空の DB で起動できない不具合が見つかった）
- **`docker compose down -v` は慎重に**: `-v` は DB のボリュームも消す。実行前に `docker compose ps` で、自分のスタックか確認する
- **マイグレーションは往復を確認する**: `downgrade` と `upgrade` を通してから取り込む。Enum 型は `op.create_table` が自動で作るので、事前の `create()` は重複エラーになる
- **破壊的な操作の前にバックアップ**: テーブル削除・downgrade は先に `infra/backup.sh` で取る
- **利用者データは外部キーの順に消す**: `refresh_tokens` → `widgets` → `workspaces`（連動して sensors・測定値・アラーム・ダッシュボードが消える）→ `users`。順番を誤ると途中で失敗する
- **DELETE では領域は戻らない**: 表を空にしたら `VACUUM FULL <表名>` で OS に返す
- **計測は、アプリを変えずに行う**: `docker run --pid=container:<backend> --cap-add SYS_PTRACE` で py-spy を別コンテナから実行する
- **負荷テストの前に Webhook の登録を確認する**: 閾値超えの値を多く送ると、アラームごとに Webhook が送られ CPU を使う（実際に起きた）
- **センサーを更新したら `updated_at` も更新する**: 一覧の ETag が古いままになる（architecture.md §4.1）
