## 製品方針

### 2026-10-01 — 拡張は Python プラグインではなく Webhook で行う
- **判断**: 業種別の拡張は、Webhook（イベントを JSON で送る）とルール設定で実現する
- **理由**: 対象は技術者でない工場スタッフ。プラグインは Python を書く必要があり、安全に配布する仕組み（サンドボックス）も無い。Webhook なら Zapier・Make・n8n などでコード無しに連携できる
- **影響**: プラグイン基盤（10-02 導入）は 10-04 に廃止。詳細は [Webhook・通知](#webhook通知)

### 2026-10-02 — 通知は Discord Webhook のみ。設定は DB に持つ
- **判断**: 基本機能の通知は Discord Webhook だけにし、SMTP（Email）は削除した。Discord の URL・有効/無効・再通知の設定は、`.env` ではなく DB に保存し、設定画面から変えられる
- **理由**: 記録なし（プロジェクトの方針）
- **影響**: 他サービスへの通知は Webhook で行う。通知設定がワークスペースごとになった経緯は [認証・SaaS](#認証saas)

## データモデル

### 2026-10-02 — アラームは 2 段階、しきい値は 4 項目、解除には不感帯を置く
- **判断**: 重要度は軽故障（warning）と重故障（critical）の 2 段階。しきい値は「上限・下限」×「軽・重」の 4 項目。発生は閾値を超えた時点で即時、解除は閾値から不感帯の幅だけ戻ったとき（ヒステリシス）
- **理由**: 現場の要望で、「すぐ止める」と「様子を見る」の通知先・通知音を分けたい。不感帯は、閾値付近で値が揺れると発生と解除が繰り返され、通知が溢れるため
- **影響**: 重要度が変わったときは、新規アラームを作らず既存の行を更新する（履歴が増えすぎないため）。3 段階以上が必要になったら再検討する

### 2026-10-02 — センサーは物理削除、ダッシュボードは論理削除
- **判断**: センサーを削除すると、測定値とアラームも削除する（ウィジェットは残し、紐付けだけ外す）。ダッシュボードは `deleted_at` による論理削除のまま
- **理由**: センサーを論理削除にすると、削除済みと同名のセンサーを登録できず利用者が混乱した。ダッシュボードには同名の再登録の問題が無い
- **影響**: アラーム履歴は失われる。監査用に残す要件が出たら再検討する
- **注意**: DB の CASCADE だけでは足りなかった。SQLAlchemy が削除前に子の行を読み、外部キーを NULL にしようとするため。`passive_deletes` を設定し、DB 側の連動削除に任せている

### 2026-10-02 — 生産数は「時間・日・目標達成率」。OEE は見送り
- **判断**: 「直近 1 時間」「本日累計」「本日の目標達成率」を集計する。OEE は採用しない
- **理由**: OEE には停止理由の記録とシフトのカレンダーが要る。複雑な生産管理は作らないという現時点の方針に反する

### 2026-10-12 — 未使用の `widget_configs` テーブルを削除
- **判断**: ウィジェットの設定は `widgets.config` に持つため、使われていない `widget_configs` をマイグレーション `e5f6a7b8c9d0` で削除する。downgrade では空のテーブルを再作成する。SaaS → OSS の移行と復旧ツールの対象からも外す
- **理由**: 本番・OSS 版とも 0 件で、アプリが書き込む箇所も無かった
- **影響**: スキーマの版が変わるため、適用前のバックアップは、復旧ツールの書き戻し・マージには使えない（同じ版どうしに限る）。`infra/restore.sh` で丸ごと戻してからアプリを起動すれば、`alembic upgrade head` で削除される。マイグレーションを足すときは、版を固定している箇所（e2e の移行画面のテスト）も更新する

## 技術選定

### 2026-10-02 — DB は PostgreSQL 15 のみ
- **判断**: 開発・テスト・本番のすべてで PostgreSQL 15 を使う（テストも PostgreSQL に接続する）
- **理由**: 記録なし。当初は開発・テストに SQLite を使う想定だったが、全環境を PostgreSQL に統一した

### 2026-10-02 — TimescaleDB は見送り
- **判断**: 複合インデックス `(sensor_id, recorded_at)` で対応する
- **再検討の目安**: 測定値が 1,000 万行を超える、またはダッシュボードのクエリが 500 ms を超える
- **追記（2026-10-25、Mac の Docker で実測。TimescaleDB 2.28.3 / PostgreSQL 15、10 センサー・5 秒間隔・時刻にゆらぎ・200 万行）**: 圧縮は 161 B/行が約 12 B/行（約 93% 減）で効果は大きい。ただし ①圧縮済みの塊への `DELETE`/`UPDATE` は既定の上限（10 万行）で失敗する（`purge.py` の `DELETE` を `drop_chunks` に変える必要）、②圧縮済みの塊への `INSERT` は約 7,000 行/秒で、素の約 12.7 万行/秒の 1/18（復旧ツールの書き戻しが遅い）、③ダンプは `timescaledb` 拡張なしの PostgreSQL に戻せない（復旧ツール・OSS 版との行き来に影響）、④主キーに時刻が要る。拡張に依存しない方法を先に採ったので（次の項目）、見送りを続ける

### 2026-10-25 — readings の主キーを (sensor_id, recorded_at) に統合する
- **判断**: `readings` から連番の `id` を廃止し、主キーを `(sensor_id, recorded_at)` にする。索引 `ix_reading_sensor_recorded` は主キーの索引と重複するので持たない（マイグレーション `g7b8c9d0e1f2`）。API の応答（`ReadingRead`）からも `id` を外す
- **理由**: 実測（PostgreSQL 15、10 センサー・5 秒間隔・時刻にゆらぎ、200 万行）で、1 行 161 B → 101 B（約 4 割減）。500 万行の書き込みは 8.3 秒 → 5.6 秒。検索（直近 1000 件・25 日の間引き・7 日の集計・1 時間の範囲）は同等（差は 1 割以内）。期間削除の `DELETE` も 881 ms → 683 ms。拡張は不要で、`pg_dump` / `restore.sh` / 復旧ツールの手順そのものは変わらない（ただし下の「影響」のとおり、適用前のバックアップは書き戻しに使えない）。測定値はまだほとんど無く、影響が最小のうちに行う
- **取り込みの扱い**: 1 回の送信内の複数の値は、同じ `recorded_at` を持っていた。主キーにすると 2 件目以降が重複になるため、センサーごとに「前に割り当てた最後の時刻」をメモリに覚え、次の送信はそれより必ず 1 マイクロ秒以上進めて割り当てる（送信内の値も、別々の送信も重ならない。時計が戻っても重ならない。`api/ingest.py`）。それでも主キーが重なる場合（サーバーを複数プロセスで動かす、再起動直後に時計が戻る、commit の応答が失われた後の再試行など）は、`ON CONFLICT DO NOTHING` で書かずに続け（バッチ全体は失敗しない）、実際に書けた値だけをアラーム評価・通知・件数に使い、書かなかった件数を警告ログに出す。1 回の flush は 5,000 行ずつの INSERT に区切る（asyncpg は 1 文のパラメータが 32,767 個までで、全行を 1 文にすると 1 万件余りで失敗し続け、取り込み全体が止まる）。デバイスの再送で同じ値が二度届いても、受信時刻が新しいので重複とは見なされず、従来どおり二重に保存される
- **移行**: 新しいテーブルへ写す。旧データは 1 行も捨てない（2026-10-29 に変更。当初は同じ時刻の重複を 1 行に減らしていたが、公開前に、利用者のデータを黙って消さない形に直した）。同じ (sensor_id, recorded_at) の旧データは、id が小さい 1 行を元の時刻に、残りを空いている時刻まで 1 マイクロ秒ずつずらして入れ、最後に件数を比べて、合わなければ移行全体を取り消す。書き込みを止めるロック（SHARE モード）を取り、終了時に `ANALYZE` する。稼働中のアプリがあるときは実行しない。一時的に旧テーブルと新テーブルの両方と WAL・並べ替えの一時ファイルが要るので、readings の 2 倍程度の空きを目安にし、更新の前に `infra/check-migration-space.sh` で確かめる（実測: 500 万行・10 センサーで 13 秒、766 MB → 481 MB。1 億行規模は未測定）。downgrade は `id` を時刻順に振り直して戻す
- **保持期間の削除**: `purge.py` は `id` で絞っていたので、主キーの組 `(sensor_id, recorded_at)` で絞って消す形に直した（2026-10-29、保持 14 日の変更と合わせたとき）
- **見送った案**（いずれも同じ条件で、容量は実測。検索速度の実測は B と C のみ）: センサー番号を `smallint`、値を `float4` にする案 C（83.8 B/行でさらに 17% 減。UUID との対応表と精度の確認が要る）、索引を BRIN だけにする案（52.2 B/行。センサー数が増えると遅くなる見込みだが、速度は未測定）、1 時間 1 行の配列にする案（8.9 B/行で約 95% 減だが取り込み・アラーム・間引き・復旧ツールを作り直す）。必要になったら再検討する
- **影響**: スキーマの版が変わるため、適用前のバックアップは、復旧ツールの書き戻し・マージには使えない（同じ版どうしに限る）。版を固定している e2e の移行画面のテストを更新した

### 2026-10-02 — 画面の更新は 5 秒ごとのポーリング
- **判断**: WebSocket は使わない。一覧・最新値・アラームは 5 秒ごと、グラフの直近モードは 30 秒ごとに取り直す
- **理由**: 実装が単純。WebSocket は後のフェーズで検討する方針
- **再検討の目安**: 低遅延が必須の利用者が出たとき

### 2026-10-25 — AWS は「災害時だけ起動する控え」にし、バックアップは Cloudflare R2 に送る
- **判断**: 平常時の本番は Proxmox のまま。AWS には EC2・EBS・パブリック IPv4 を置かず、バックアップを R2 に置き、設定済み EC2 の AMI（スナップショット）だけを持つ。災害時に AMI から起動し、R2 から戻す。バックアップの送信は、既存の `infra/offsite-s3.sh` をそのまま使う（`AWS_ENDPOINT_URL` で R2 に向ける）
- **理由**: 利用者が実質ゼロで、冗長化の費用を払う段階にない。常時稼働の最小構成でも月 $10 前後かかる（EC2 のスポットが中心）のに対し、この形なら月 $0〜2。R2 は保管 10GB まで無料で、外向き通信も無料
- **R2 の安全策**: R2 のトークンは追加だけの権限にできないので、バケットのロック（保持期間）で、削除・上書きを防ぐ
- **見送った案**: スポット 1 台＋ EBS ＋ WAL を S3 へ（月 $10〜、数分で復旧）、2 台構成（DB の複製。月 $19〜）、Lambda（バックエンドの作りと合わない）。利用者が増えたら、スポット 1 台に上げる。EFS（NFS）に PostgreSQL を置く案は、PostgreSQL の要件（`hard` マウント、二重起動で破損）と遅さから採らない
- **再検討の目安**: 利用者が付く、または停止を数十分以上許せなくなったとき
- **未確認**: R2 への実機での送信、AMI からの復旧の訓練、IPv6 のみの VPC（GitHub は IPv4 専用なので、イメージは CI でビルドして Docker Hub 経由で配る案が有力）

## 認証・SaaS

### 2026-10-03 — SaaS はマルチテナント（共有 DB + `workspace_id`）
- **判断**: テナントごとに DB を分けず、同じ DB の中でワークスペース単位に分離する
- **理由**: 記録なし
- **self-hosted との関係**: `workspace_id` が `NULL` のデータが self-hosted。`AUTH_MODE`（`disabled` / `multi_tenant`）で切り替える

### 2026-10-03 — Free Tier の制限
- **判断**: センサーは 10 個まで（超過は 402）。測定値は 14 日で削除（SaaS のセンサーのみ。self-hosted は対象外。当初 90 日、2026-10-28 に 14 日へ変更）
- **理由**: 記録なし。超過分は将来の有料プランで対応する方針

### 2026-10-03 — 管理者アカウントは DB に入れない
- **判断**: 管理者は、サーバー上のテキストファイル（bcrypt ハッシュ）で管理する
- **理由**: 記録なし。運用者だけが使うアカウントを、利用者のデータと分けるため
- **影響**: ファイルは DB のバックアップに含まれない。別に保管する

### 2026-10-04 — センサー名はワークスペース内で一意、取り込みキーは全体で一意
- **判断**: センサー名はワークスペース内で一意（self-hosted は NULL 用の部分インデックス）。取り込みキー（`ingest_key`）は全体で一意のまま
- **理由**: 名前を全体で一意にしていたため、別のワークスペースが同じ名前を使えなかった。取り込み API はキーだけでセンサーを特定するので、キーは全体で一意である必要がある
- **影響**: 他のワークスペースのキーと衝突すると 409 を返す。その応答から、キーが使われていることが分かる（存在の確認になる）。ワークスペースごとにキーを分けるには、取り込みの形式を変える必要がある

### 2026-10-04 — 通知設定はワークスペースごとに 1 行
- **判断**: アラームは、そのセンサーのワークスペースの設定で送る。設定が無いワークスペースは、Discord 通知をしない。再通知の判定も、そのワークスペースの設定に従う
- **理由**: ID=1 の 1 行に固定していたため、SaaS のアラームが他のワークスペースの設定で送られるおそれがあった

### 2026-10-04 — リフレッシュトークンは使うたびにローテーション
- **判断**: 使ったトークンは即時に失効し、新しいトークンを発行する
- **理由**: 盗まれたトークンの再利用を見つけやすくするため
- **影響**: 失効済みトークンの再利用を検知する仕組みは無く、401 を返すだけ。期限切れの行の掃除は [性能](#性能)

### 2026-10-12 — メールは小文字にそろえ、`lower(email)` の一意インデックスで重複を防ぐ
- **判断**: 登録・ログイン・管理者のメール修正では、前後の空白を除いて小文字にし、DB との比較は `lower(email)` で行う。マイグレーション `a7b8c9d0e1f2` で `users(lower(email))` の一意インデックス `ix_users_email_lower` を足す。大文字小文字だけが違う重複が既にあると、重複したメールを示してマイグレーションが失敗する（何も削除しない）。同時登録による一意制約違反は、500 ではなく 409
- **理由**: 以前は、大文字小文字が違うメールが別のアカウントになった。`lower()` で比較すると、素の列のインデックスが使われず、ログインのたびに全件を走査する（5,000 行の `EXPLAIN` で、Index Scan のコスト 8.30、Seq Scan は 122）
- **影響**: 復旧ツールのマージで、大文字小文字だけが違うメールが両側にあると、この一意インデックスに違反して失敗する。登録時の「既に登録されている」という応答から、登録の有無が分かる点は、方針が未決定
- **ログインの応答時間**: 未登録のメールでも、ダミーのハッシュ照合（同じコスト係数 12）を行い、応答時間から登録の有無を推測されないようにする

### 2026-10-12 — パスワードは UTF-8 で 72 バイト以内。422 の応答に入力値を含めない
- **判断**
  - 登録と管理者のパスワード変更: 72 バイトを超えたら 422（`password_too_long`）
  - ログインと管理者ログイン: 72 バイトを超える、または UTF-8 にできない文字（孤立サロゲート）を含むパスワードは、未登録・誤りと同じ 401
  - 全 API の 422 の応答から、送信された値（`input`）と `ctx` を除く（`app/validation.py`）
- **理由**: bcrypt は 72 バイトを超えると `ValueError` を出し、500 になっていた。日本語は 1 文字 3 バイトなので、25 文字ほどで起きた。修正前は、422 の応答（例: パスワードが短すぎる）に、平文のパスワードが入っていた
- **影響**: 72 バイト以内の既存のハッシュ・ログインは変わらない。`input` と `ctx` を読むクライアントは無かった。`msg` には最大長などの値が残る

### 2026-10-12 — bcrypt は別スレッドで、同時 4 件まで
- **判断**: 登録・ログイン・管理者ログイン・パスワード変更の bcrypt を、`asyncio.to_thread` で別スレッドに出し、`asyncio.Semaphore(4)` で同時 4 件に制限する（`app/auth.py` の `run_blocking_auth`）。ダミー照合も、別スレッドで同じコスト係数で行う
- **理由**: `async def` の中で bcrypt（約 200ms の CPU 処理）が同期的に走り、取り込みや `/health` を含む、同じプロセスの全要求が止まっていた。実測で、ログイン中の別の処理の最大遅延は、216〜228ms から 12ms 以下になった
- **影響**: ログインにはレート制限（20 回/分、登録は 10 回/分）があるので、同時 4 件の待ち行列で足りる。管理者ログインを同時に投げた直後に、`/health` が 450〜700ms 遅れることが 1 回あった（原因は未調査）

### 2026-10-18 — self-hosted の取り込みは、設定でキーなしにできる（`INGEST_AUTH=off`）
- **判断**: 環境変数 `INGEST_AUTH`（`key` / `off`、既定 `key`）を足した。`off` のときは、self-hosted の取り込みで `X-API-Key` を確かめない（送られてきたヘッダーは無視する）。センサーは、本文の `ingestKey` だけで識別する（SaaS と同じ）。`off` のときは `INGEST_API_KEY` を使わないので、本番の既定値の検査もしない。SaaS（`multi_tenant`）では何も変わらない
- **理由**: 機器（M5Stack など）に、長い共有キーを入れたくない。キーの入力が現場での設定の手間になり、全機器に同じキーを配るため、1 台から漏れると全台に影響する。空のキーを「キーなし」と読み替える案は、設定の入れ忘れで意図せず開いてしまうので避け、明示の設定にした
- **影響**: `off` では、`ingestKey` を知っていれば誰でも値を書ける（ほかの API は変わらない）。取り込みの口を LAN などに限定して使う。起動時に警告をログに出す。IP ごとのレート制限は残るが、鍵は `CF-Connecting-IP` を優先して読むので、プロキシを通らず直接届く経路ではヘッダーの偽装で避けられる（口の前のプロキシで外す）。誤字（`of` など）は起動時にエラーにする。機器側は、`FactorEyeClient`（Arduino）が、キーが空なら `X-API-Key` を付けない

### 2026-10-19 — self-hosted は、未登録の ingestKey のセンサーを自動で作れる（`INGEST_AUTO_CREATE=on`）。SaaS は対象外
- **判断**: 環境変数 `INGEST_AUTO_CREATE`（既定 `false`）が on のとき、self-hosted の取り込みで、未登録の `ingestKey` を 404 にせず、センサーを自動で作る。機器が本文に付けた `name`・`unit` を使う。作るのは、`ingestKey` が英数字と `. _ -` で 64 文字まで、かつセンサーの総数（無効なものも数える）が `INGEST_AUTO_CREATE_MAX_SENSORS`（既定 100）未満のときだけ。`name`・`unit` は、拒否せず、制御文字などを除いて整える（機器が 4xx で値を捨てないため）。作る処理は、advisory lock で 1 つずつ行う（上限を同時に超えられない）。SaaS（`multi_tenant`）では使えず、無視する
- **理由**: 機器を増やすたびに、FactorEye の画面でセンサーを登録するのが手間（M5Stack の複数台・複数のセンサー）。SaaS は、取り込みが `ingestKey` だけでワークスペースを決めるので、未登録のキーからは、作る先が決まらない。使うには、ワークスペース単位の機器登録用のキーが要る（別の設計）
- **影響**: on の間は、打ち間違いの ID でも、センサーが増える（上限で止まる）。削除したセンサーも、次の送信で、また作られる。`INGEST_AUTH=off` と組み合わせると、LAN の誰でも、上限までセンサーを作れる（取り込みの口を LAN に限定する）。`ingestKey` を作る文字・長さは、通常の登録（`SensorCreate`）より厳しい。起動時に警告を出す。Arduino の `FactorEyeClient` は、`setSensorInfo` で名前と単位を結びつけ、最初に送信が成功するまで、本文に付ける

### 2026-10-12 — 本番は `CHANGE_ME` などの仮の秘密値では起動しない
- **判断**: `ENVIRONMENT=production` で、`JWT_SECRET`（`multi_tenant`）または `INGEST_API_KEY`（それ以外）が、空、または `change-this`・`change_me`・`change-me` で始まる値のときは、起動を拒否する（前方一致。`a1b2changeme` や 16 進の値は通る）
- **理由**: 以前は `change-this-in-production` との完全一致だけを検査していたため、`.env.cloud.example` の `CHANGE_ME_*` のままでも起動し、公開されている値で JWT が署名された

### 2026-10-04 — プラグイン基盤を廃止（Phase 2）
- **判断**: `app/plugins/`、`/api/plugins`、関連テーブル（`plugins` / `plugin_configs`）を削除する
- **理由**: 10-01 の方針に従い、使われない拡張の仕組みを残さないため。利用例は、サンプルの `reading_logger` だけだった
- **影響（破壊的変更）**: プラグインの設定値は失われる。downgrade はテーブル定義だけを戻し、データは戻らない

### 2026-10-04 — Webhook と Discord の送信先を検証する（SSRF 対策）
- **判断**
  - Webhook: `https` のみ。名前解決した全アドレスが公開 IP のときだけ送る。登録時と送信直前の両方で検証し、リダイレクトは追わない
  - Discord（2026-10-12 に追加）: 通知設定の URL を、Webhook と同じ検証に通し、不可なら 422。送信直前にも再検証する。許可リスト（discord.com のみ）にはしない
  - 送信失敗のログには、ホスト名と HTTP 状態（または例外の型名）だけを出す
- **理由**: 利用者が指定した URL にサーバーから送るため、そのままでは社内ネットワークやクラウドのメタデータにアクセスされるおそれがあった（SaaS では他の利用者にも開かれる）。Discord の URL も、以前は内部アドレスを登録でき、失敗のログにはトークンを含む秘密の URL が出ていた。許可リストにしないのは、Mattermost など互換サーバーを塞がないため
- **例外**: `WEBHOOK_ALLOW_PRIVATE_NETWORKS=true` で、社内ネットワークを許可できる（自己ホストで社内の自動化基盤を使う場合のみ。既定は禁止）
- **残るリスク**: DNS rebinding（検証と接続の間に DNS の結果が変わる）は、Webhook・Discord とも未対策。接続先の IP を固定すれば防げる

### 2026-10-08 — Webhook の送信は接続を使い回し、同時送信と待ちに上限を置く
- **判断**: 共有のクライアントで接続を使い回す。同時送信は 10 件まで、送信待ちは 1,000 件まで。超えた分は送らずに捨て、件数をログに出す（多くても 1 分に 1 回）
- **理由**: 値の受信ごと・アラームごとに送るため、大量の取り込みや送信先の遅延で、送信のタスク・DNS 検証（スレッド）・接続が際限なく増えていた。ラズパイの負荷テストでも、Webhook の送信が CPU を使った（[運用上の注意](#運用上の注意)）
- **影響**: 上限を超えると Webhook が届かないことがある（再試行はしない方針のまま）。確実な配送が必要になったら、送信キューと再試行を検討する

### 2026-10-12 — デバイスクライアントの再送ルール
- **判断**: Raspberry Pi と Arduino/M5Stack のクライアントは、エラーの種類で次のように分ける

  | 送信結果 | 動き |
  |---|---|
  | 通信エラー・5xx・408・429 | 再送する。429 の `Retry-After` は、付いていれば最大 5 分まで尊重する（現行の backend は付けない） |
  | 400・422 など、再送しても成功しない 4xx | その送信分を捨てて警告する |
  | 401・403・404（キーの誤り・センサーの無効化・未登録） | 設定の誤りなので、値を捨てずに保持して再送する。1 センサー 10 件まで、超えたら古い値から捨てる。他のセンサーのバックオフとバッファは巻き込まない |
  | NaN・Infinity・型違いの値 | `send()` の入口で捨てる |
- **理由**: 以前は 4xx も再送していたため、NaN を 1 件送ると 400 が続き、そのセンサーは最大約 100 件の間、送れなくなった
- **影響**: センサーを登録する前にデバイスを動かし始めても、登録後に、保持した値（10 件まで）が届く。仕様は architecture.md §9

## データ移行

SaaS → OSS の移行は、書き出しファイルを介して行う。OSS → SaaS は復旧ツール側で扱う（[バックアップ・復旧](#バックアップ復旧)）。

### 2026-10-04 — 書き出しファイルを介して移行する
- **判断**: 移行元（SaaS）と移行先（OSS）を直接つながず、gzip の JSON Lines の書き出しファイルを介する。書き出しは SaaS の本人だけ、取り込みは OSS のみ
- **理由**: 両方が同じ DB に同時に存在する必要がない。ファイルなら、確認（件数の dry-run）も保管もでき、失敗しても何も残らない
- **影響**: 取り込み API に認証は無い（OSS の前提）。インターネットに直接公開しないこと
- **後継**: self-hosted にも書き出しを足した（次の項目）

### 2026-10-08 — self-hosted にも書き出しを足し、OSS → OSS を完結させる
- **判断**: 書き出しを self-hosted でも使えるようにする（`workspace_id IS NULL` の全データが対象）。OSS → SaaS（ワークスペースを選んでの取り込み）は、このアプリではなく復旧ツール側で扱う
- **理由**: self-hosted の読み取り API はもともと認証が無く（architecture.md §11 の前提）、全データが `GET` で読める。書き出しを足しても、読めるものは増えない。一方 OSS → SaaS には、ワークスペースの選択・Free Tier の確認など、認証を前提とする判断が要る。無認証のこのアプリではなく、運用者が操作する復旧ツールに置く
- **影響**: self-hosted どうしの移行・バックアップは、アプリ内の「データ移行」だけで完結する。OSS → SaaS には復旧ツールが要る

### 2026-10-04 — ファイルの内容と範囲
- **ID と取り込みキーは保つ**: センサー・ダッシュボードなどの UUID と `ingest_key` は、そのまま移す。測定値の ID は振り直す
  - 理由: デバイス側の設定（取り込みキー）を変えずに済ませるため。測定値の連番は、移行先の連番と衝突させない
  - 影響: 同じワークスペースを同じ DB に取り込み直すと、ID が重なって失敗する（何も残らない）。削除済みのダッシュボードも行が残るため、同様に失敗する
- **測定値は差分の配列で書く（形式の版 2）**: センサーごとに `[値, 前の行からの差分（マイクロ秒）]` の配列にして、5,000 件ずつ 1 行に書く
  - 理由: JSON のキー名と ID を毎行書くと約 14 バイト/件。配列と差分にすると約 6 バイト/件で、約 6 割減る。時刻はマイクロ秒を保つので、往復で完全に戻る（ミリ秒への丸めは見送り）
  - 影響: 版 1 のファイルは取り込めない（版 1 は未リリースのため、互換性は持たない）
- **通知設定とユーザーは移さない**: ユーザー・リフレッシュトークン・ワークスペースは移さない。通知設定（Discord の URL）は、`with_notifications` を指定したときだけ移し、移行先の ID=1 を上書きする
  - 理由: OSS には認証が無い。通知の URL は、移行先で意図して設定するべき値

## バックアップ・復旧

すべて 2026-10-08 の判断。復旧ツールは `tools/recovery/`。

### 本体と別のプログラムにする
- **判断**: バックアップの確認・書き戻しは、FactorEye の管理画面ではなく、別のプログラムで行う。Docker があればどこでも動き、設定だけを変える
- **理由**: 不正アクセスでプログラムを壊されたときや、DB が壊れて backend が起動しないときにこそ使う道具だから。インターネットに公開している画面に、「バックアップを読む」「DB に書き込む」機能を置かないため
- **影響**: 画面は Basic 認証で、待ち受けは既定で 127.0.0.1。本番では本体と別の compose で動かし、本体のデプロイの影響を受けない

### 展開は、改ざんされている前提で行う
- **判断**: SQL を自分で解釈せず、作業用の Postgres に流し込んでから調べる。流し込みは、psql の `\restrict`・管理者ではないロール・秘密を渡さない環境で行う
- **理由**: sha256 の記録もバックアップと一緒に作り直せるため、検証だけでは改ざんを防げない。QA のレビューで、展開時に任意のコマンドが実行されうることが分かった
- **影響**: 所有者が管理者のロールのバックアップや、行頭にメタコマンドのあるバックアップは展開しない

### 書き戻しは「無い行を足す」だけ
- **判断**: 今ある行は変えない・消さない。試行は同じ処理を取り消す。実行は、確認した件数と一致したときだけ、直前に今の DB を控えてから、1 トランザクションで行う
- **理由**: 復旧の操作で、今あるデータを壊さないため。件数の見込みと実際がずれる余地を無くすため
- **影響**: 「バックアップの時点の値に戻す（上書き）」はできない。必要なら、控えと `infra/restore.sh` で丸ごと戻す

### 測定値は（センサー, 時刻）で同じ行かを判定する
- **判断**: 測定値の連番の id は持ち込まず、（センサー, 時刻）が今の DB に無いものだけを足す
- **理由**: DB を作り直すと連番が最初から振られ、バックアップの id と、別の測定値の id が重なるため
- **影響**: 同じセンサー・同じ時刻の測定値は、1 つとみなす

### OSS 版 ⇄ SaaS 版は、所属を付け替えて書き戻す
- **判断**: OSS 版のデータは、SaaS 版の選んだワークスペースへ入れる。SaaS 版のワークスペースは、OSS 版のデータとして入れる。今の DB がどちらの版かは、`TARGET_MODE` で明示する
- **理由**: 運用者から「止めるのではなく、できるように」との指示があった。版をデータの中身で判定すると、空の SaaS 版を OSS 版と取り違える
- **影響**: 書き戻しを使うときは `TARGET_MODE` が必須。付け替えのときは、ユーザー・ワークスペースの行は入れない

### バックアップは権限 640。本番の外の控えは、本番から消せない形にする
- **判断**: バックアップは、所有者とグループだけが読める。S3 は「追加だけ」の鍵とバージョニング、別のマシンは本番から「読むだけ」の鍵（`rrsync -ro`）で取りに行く
- **理由**: バックアップには、利用者のデータとパスワードのハッシュが入る。乗っ取られた本番から、外の控えを消されないようにするため
- **影響**: 復旧ツールのコンテナは、バックアップのグループ（`BACKUP_GID`）で読む

## 性能

### 2026-10-05 — 一覧の応答は ORM を通さず、JSON を 1 回だけ作る
- **判断**: 測定値・アラーム・センサーの一覧は、必要な列だけを読み、Pydantic のモデルから JSON を 1 回だけ作って返す（`app/api/responses.py`）。OpenAPI の定義は `response_model` で残す
- **理由**: py-spy の計測で、CPU の大半は ORM のオブジェクト生成と、FastAPI の二重の変換（モデル → dict → 検証 → JSON）だった
- **影響**: 応答の形（camelCase の項目）は変わらない。列を追加するときは、一覧の列の定義（`_LIST_COLUMNS` など）にも追加する

### 2026-10-05 — アラーム一覧はページングし、警告の表示は 100 件まで
- **判断**: `GET /api/alarms` に `limit`（1〜500、省略時は全件）と `offset` を追加する。警告の表示は、発生中と確認済みを、それぞれ新しい順に 100 件まで取る
- **理由**: 全件の応答は約 210KB・約 0.4 秒で、取り直しのたびに CPU を使っていた（アラームが増えるほど重くなる）
- **影響**: API の既定の動きは従来どおり（全件）。`total` は、ページで区切る前の件数になった。確認済みが 100 件を超えると、古いものは警告の表示には出ない（設定画面では見られる）

### 2026-10-05 — センサー一覧は ETag で 304 を返し、版ごとに JSON を保持する
- **判断**: 版（ETag）は、件数と最終更新時刻から作る。`If-None-Match` が一致すれば 304（本体なし）。完成した JSON を、版ごとにプロセス内に保持する（上限 32 件）
- **理由**: 画面と負荷テストが数秒ごとに全件を取り直し、300 件分の変換が CPU の大部分を使っていた。版が変わらない間は、読み出しも変換もやり直す必要が無い
- **影響**: センサーを変更するときは、必ず件数か `updated_at` を変えること（既存の更新処理は `updated_at` を更新する）。更新で `updated_at` が変わらないと、古い一覧が返る（architecture.md §4.1）。キャッシュはプロセスごとに持つ（ワーカーを増やすと、ワーカーごと）

### 2026-10-12 — flush は読み込みを減らし、稼働ステータスは最新の 1 件だけ取る
- **判断**
  - 取り込みバッファの flush（`flush_once`）は、センサーを 1 回の `select` で読み、結果を、アラームの判定と通知に引数で渡す（以前は 3 回）
  - commit 後の Webhook 配信には、commit 前に作ったプレーンな値を渡す（commit 後の ORM オブジェクトへのアクセスは、非同期では例外になる）
  - 稼働ステータスのウィジェットは、測定値を 500 件ではなく最新の 1 件だけ取る（クエリキーに `limit` を含める）
- **理由**: flush は、クエリが 10 本から 8 本になった（センサー 100 個・値 1,000 件で、所要時間は約 73ms から 69ms。差は小さい）。稼働ステータスは、5 秒ごとに約 60KB を取りながら、使うのは最新の 1 件（約 0.12KB）だけだった
- **影響**: 挙動の差は 1 点だけ。commit 後にセンサーが削除された、またはワークスペースが変わった場合、以前は 3 回目の読み直しで未登録扱いになり、self-hosted の購読へ誤って送り得た。今は commit 前の値で送る

### 2026-10-12 — 期限切れの `refresh_tokens` を毎日削除する
- **判断**: 毎日 UTC 03:00 の `purge_loop` で、`expires_at` が 7 日より前の行を、1,000 件ずつ別トランザクションで削除する。期限内の行は、失効済み（ローテーション後・ログアウト後）でも残す
- **理由**: ログイン・更新のたびに 1 行増え、削除する処理が無かった。失効済みトークンの再利用を検知する仕組みは無いので、行を消しても安全性は変わらない。7 日は、障害調査用の余裕
- **影響**: `expires_at` に索引が無く、削除は全件走査になる（5,000 件で 0.02 秒。数万行までは問題ない）。増えたら索引を足す（マイグレーションが要る）

### 2026-10-28 — 控え（AWS）が稼いだデータの本番への書き戻しは、管理画面のボタンから復旧ツールを呼ぶ
- **判断**
  - **入口**: 本番アプリの `/admin` に「書き戻し」の区画を置く（一覧 → 試算 → 確認の小窓 → 実行 → 結果）。API は `/api/admin/failback/{handoffs,preview,apply}`（管理者トークン。`AUTH_MODE=multi_tenant` のときだけマウントする既存の仕様のまま）

  - **範囲**: 縮小ダンプの全ワークスペース（OSS 版の今の DB なら、ワークスペースに属さないデータ）。縮小ダンプは小さい表が全体、`readings`・`alarms` が起点以降なので、既存の `merge`（無い行だけ・`readings` は（センサー, 時刻）で重複回避・int 採番の `setval`・発生中のアラームの重複は解除済みにして戻す）で正しく扱える。縮小ダンプ相当のデータで試験した（`tools/recovery/tests/test_handoff.py`）

## 運用上の注意

これまでの作業で起きた問題から、次の点を守ること。

**テスト・環境**
- **テスト DB を分ける**: backend のテストは、接続先のすべてのテーブルを作り直して削除する。開発用・本番用の DB に向けるとデータが消える（実際に起きた）。テスト専用の DB を指定すること
- **フレッシュな環境で一度は通す**: ローカルの使い回しの DB では、マイグレーションの未適用やヘルスチェックの競合が見えない。リリース前に、CI のような空の環境での起動を一度行う（実際に、空の DB で起動できない不具合が見つかった）
- **`docker compose down -v` は慎重に**: `-v` はボリューム（DB のデータ）も削除する。実行前に `docker compose ps` で、自分が起動したコンテナか確認する。他の人が使っている可能性のあるスタックには使わない

**マイグレーション・データ削除**
- **マイグレーションは往復を確認する**: `alembic downgrade` と `upgrade` を通してから取り込む
- **Enum 型のマイグレーション**: `op.create_table` は Enum 型を自動で作るので、事前の `create()` は重複エラーになる。`add_column` は事前の作成が要る。挙動が異なるので注意する
- **バックアップを取ってから破壊的な操作をする**: DB を消す操作（テーブル削除・マイグレーションの downgrade）は、先に `infra/backup.sh` で取る
- **利用者データは外部キーの順に消す**: `refresh_tokens` → `widgets`（`dashboards` を参照）→ `workspaces`（連動して `sensors`・測定値・アラーム・ダッシュボードが消える）→ `users`。`NO ACTION` の参照があり、順番を誤ると途中で失敗する（トランザクションで囲み、件数を確かめてから確定する）
- **消した後は領域を戻す**: DELETE では、DB の使用量はすぐには減らない（PostgreSQL は領域を再利用するだけ）。表が空になったら、`VACUUM FULL <表名>` で OS に返す

**計測・負荷テスト**
- **性能の計測は、アプリを変えずに行う**: `docker run --pid=container:<backend> --cap-add SYS_PTRACE` で、別のコンテナから py-spy を実行する。関数ごとの配分は近似（応答の変換は、どの API から来たか分かりにくい）
- **負荷テストの前に Webhook の登録を確認する**: 負荷テストは閾値を超える値を多く送るため、アラームごとに Webhook が送られ、CPU を使う（実際に起きた）。テスト前に登録を確認し、不要なものは消す

**実装**
- **センサーを更新したら `updated_at` を更新する**: センサー一覧の版（ETag）は、件数と `updated_at` で判定している（architecture.md §4.1）。`updated_at` が変わらないと、古い一覧が返る

**SaaS の測定値の保持期間（2026-10-28）**
- **判断**: SaaS（Free Tier）の測定値の保持を、**90 日から 14 日**にする。self-hosted は無期限のまま
- **理由**: DR（AWS の控えへの復旧）のデータ量と復旧時間を小さくするため。500 センサー × 5 秒（約 100 件/秒）で、DB 全体が約 100 GB → 約 12 GB、最初のベースバックアップの送信が 8〜22 時間 → 約 1〜3 時間になる（`ecopower` の `docs/aws-dr-wal-design.md`）
- **影響**: 次の 03:00（UTC）の削除で、14 日より古い測定値が消える（戻せない）。グラフの最長の範囲は 14 日（30 日のプリセットは SaaS では出さない）。利用規約の文言も 14 日に変更した
