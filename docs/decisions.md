# 設計判断の記録

主要な設計判断を、日付・判断・理由・影響の順にまとめたものです。仕様そのものは [`architecture.md`](architecture.md)、リリースごとの変更は [`CHANGELOG.md`](../CHANGELOG.md) を参照してください。

判断が覆った場合は、古い項目を消さずに「後継」を追記します。

## 製品方針

### 2026-10-01 — 拡張の主軸を Python プラグインから Webhook へ移す
- **判断**: 業種別の拡張は、Python プラグインではなく Webhook（イベントを JSON で送る）とルールベース設定で実現する
- **理由**: 対象は技術者でない工場スタッフ。プラグインは Python コードを書く必要があり、サンドボックスも無いため安全に配布できない。Webhook なら Zapier・Make・n8n などでコード無しに連携できる
- **影響**: プラグイン基盤（2026-10-02 導入）は 2026-10-04 に廃止（後継: 下記 Webhook）

### 2026-10-02 — アラーム通知は Discord Webhook のみ（Email 廃止）
- **判断**: 基本機能の通知は Discord Webhook のみ。SMTP 送信は削除
- **理由**: 記録なし（プロジェクトの方針として決定）
- **影響**: 他サービスへの通知は Webhook で対応する

### 2026-10-02 — 通知設定は DB で管理（`.env` から移行）
- **判断**: Discord の URL・有効/無効・再通知の設定は、設定画面から変更できるよう DB に保存する
- **理由**: 記録なし（設定画面から変更できる形が望ましいという方針）

## データモデル

### 2026-10-02 — アラームは重要度 2 段階、しきい値は 4 項目
- **判断**: 軽故障（warning）と重故障（critical）の 2 段階。しきい値は「上限・下限」×「軽故障・重故障」の 4 項目
- **理由**: 「すぐ止めるべき」と「様子を見る」で通知先と通知音を分けたい、という現場の要望
- **影響**: 重要度が変わったときは新規アラームを作らず既存行を更新する（履歴が増えすぎないため）。3 段階以上が必要になったら再検討する

### 2026-10-02 — 不感帯（ヒステリシス）を導入
- **判断**: 発生は閾値超過で即時、解除は閾値から不感帯の幅だけ戻ったときに行う
- **理由**: 閾値付近で値が揺れると、発生と解除が繰り返されて通知が溢れるため

### 2026-10-02 — センサー削除は物理削除（関連データも削除）
- **判断**: センサーを削除すると、測定値とアラームも削除する。ウィジェットは残し、紐付けだけ外す
- **理由**: 論理削除にすると、削除済みと同名のセンサーを登録できず、利用者が混乱したため
- **影響**: アラーム履歴は失われる。監査目的で残す要件が出たら再検討する
- **注意**: DB の CASCADE だけでは不十分だった。SQLAlchemy が削除前に子行を読んで外部キーを NULL にしようとするため、`passive_deletes` を設定して DB 側の連動削除に任せている

### 2026-10-02 — ダッシュボードは論理削除のまま
- **判断**: ダッシュボードは `deleted_at` による論理削除を続ける
- **理由**: センサーと違い、同名での再登録の問題がない

### 2026-10-02 — 生産数は時間・日・目標達成率で表す（OEE は見送り）
- **判断**: 「直近 1 時間」「本日累計」「本日の目標達成率」を集計する。OEE は採用しない
- **理由**: OEE には停止理由の記録とシフトのカレンダーが必要で、現時点の非目標（複雑な生産管理は作らない）に反する

## 技術選定

### 2026-10-02 — DB は PostgreSQL のみ（SQLite は使わない）
- **判断**: 開発・テスト・本番のすべて PostgreSQL 15（テストも PostgreSQL に接続する）
- **理由**: 記録なし。以前は開発・テストに SQLite を使う想定だったが、現在は全環境で PostgreSQL に統一されている

### 2026-10-02 — TimescaleDB は見送り
- **判断**: 複合インデックス `(sensor_id, recorded_at)` で対応する
- **再検討の目安**: 測定値が 1,000 万行を超える、またはダッシュボードのクエリが 500 ms を超える

### 2026-10-02 — 画面の更新は 5 秒ごとのポーリング
- **判断**: WebSocket は使わない
- **理由**: 実装が単純。WebSocket は後続フェーズで検討する方針
- **再検討の目安**: 低遅延が必須の利用者が出たとき

### 2026-10-01 — ダッシュボードは自由配置（12 列グリッド）
- **判断**: `react-grid-layout` でドラッグ配置・自由なサイズ変更。軸の範囲も後から編集できる
- **理由**: 配置とサイズの制約が強すぎるというフィードバック

## 認証・SaaS

### 2026-10-03 — SaaS はマルチテナント（共有 DB + `workspace_id`）
- **判断**: テナントごとに DB を分けず、同じ DB でワークスペース単位に分離する
- **理由**: 記録なし（共有 DB + `workspace_id` による論理分離として決定）
- **self-hosted との関係**: `workspace_id` が `NULL` のデータが self-hosted。`AUTH_MODE`（`disabled` / `multi_tenant`）で切り替える

### 2026-10-03 — Free Tier の制限
- **判断**: センサー 10 個まで（超過は 402）。測定値は 90 日で削除（SaaS のセンサーのみ）
- **理由**: 記録なし（超過分は将来の有料プランで対応する方針）。self-hosted は対象外

### 2026-10-03 — 管理者アカウントは DB に入れない
- **判断**: 管理者はサーバーのテキストファイル（bcrypt ハッシュ）で管理する
- **理由**: 記録なし（運用者だけが扱うアカウントを、利用者データと分けて管理する方針）
- **影響**: ファイルは DB バックアップに含まれないので、別途保管する

### 2026-10-04 — リフレッシュトークンは使うたびにローテーション
- **判断**: 使ったトークンは即時失効し、新しいトークンを発行する
- **理由**: 盗まれたトークンの再利用を検出しやすくするため

## 外部連携（Webhook）

### 2026-10-04 — Webhook の新設（Phase 1）
- **判断**: イベント `reading.received`（値の受信ごと）と `alarm.triggered`（アラーム発生ごと）を、任意の URL へ JSON で送る
- **理由**: 拡張の主軸（上記 2026-10-01）を実現するための最小の仕組み
- **意図的に入れなかったもの**: 再試行、送信キュー、署名。必要になった段階で追加する

### 2026-10-04 — Webhook の送信先を制限（SSRF 対策）
- **判断**: `https` のみ。名前解決した全アドレスが公開 IP の場合だけ送る。登録時と送信直前の両方で検証する。リダイレクトは追わない
- **理由**: 利用者が指定した URL にサーバーから送るため、そのままでは社内ネットワークやクラウドのメタデータへアクセスされるおそれがあった（SaaS では他の利用者にも開かれる機能になる）
- **例外**: `WEBHOOK_ALLOW_PRIVATE_NETWORKS=true` で社内ネットワークを許可できる。自己ホストで社内の自動化基盤を使う場合だけ。既定は禁止
- **残るリスク**: DNS rebinding（検証と接続の間に DNS が変わる）は未対応。接続先の IP を固定すれば防げる

### 2026-10-04 — プラグイン基盤を廃止（Phase 2）
- **判断**: `app/plugins/`、`/api/plugins`、関連テーブル（`plugins` / `plugin_configs`）を削除する
- **理由**: 上記の方針（2026-10-01）に従い、利用者が使わない拡張の仕組みを残さないため。サンプルの `reading_logger` 以外に利用例は無かった
- **影響（破壊的変更）**: プラグインの設定値は失われる。downgrade はテーブル定義のみ戻し、データは戻らない

## 運用上の注意

これまでの作業で起きた問題から、次の注意を守ること。

- **テスト DB を分ける**: backend のテストは、接続先のすべてのテーブルを作り直して削除する。開発用・本番用の DB に向けると、データが消える（実際に起きた）。テスト専用の DB を指定すること
- **`docker compose down -v` は慎重に**: `-v` はボリューム（DB のデータ）も削除する。実行前に `docker compose ps` で、自分が起動したコンテナかを確認する。他の人が使っている可能性のあるスタックには使わない
- **フレッシュな環境で一度は通す**: ローカルの使い回しの DB では、マイグレーション未適用やヘルスチェックの競合が見えない。CI のような空の環境での起動を、リリース前に一度行う（実際に、空の DB で起動できない不具合が見つかった）
- **マイグレーションは往復を確認する**: `alembic downgrade` と `upgrade` を通してから取り込む
- **Enum 型のマイグレーション**: `op.create_table` は Enum 型を自動で作るため、事前の `create()` は重複エラーになる。`add_column` は事前の作成が必要。挙動が異なるため注意する
- **バックアップは取ってから破壊的な操作をする**: DB を消す操作（テーブル削除・マイグレーションの downgrade）は、先に `infra/backup.sh` で取得する
