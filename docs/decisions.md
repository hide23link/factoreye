# 設計判断の記録

主要な設計判断を、日付・判断・理由・影響の順にまとめたものです。仕様そのものは [`architecture.md`](architecture.md)、リリースごとの変更は [`CHANGELOG.md`](../CHANGELOG.md) を参照してください。

判断が覆った場合は、古い項目を消さずに「後継」を追記します。

## 製品方針

### 2026-10-01 — 拡張の主軸を Python プラグインから Webhook へ移す
- **判断**: 業種別の拡張は、Python プラグインではなく Webhook（イベントを JSON で送る）とルールベース設定で実現する
- **理由**: 対象は技術者でない工場スタッフ。プラグインは Python コードを書く必要があり、サンドボックスも無いため安全に配布できない。Webhook なら Zapier・Make・n8n などでコード無しに連携できる
- **影響**: プラグイン基盤（2026-10-02 導入）は 2026-10-04 に廃止（後継: 下記 Webhook）

### 2026-10-02 — アラーム通知は Discord Webhook のみ（Email 廃止）
- **判断**: 基本機能の通知は Discord Webhook のみ。SMTP 送信は削除
- **理由**: 記録なし（プロジェクトの方針として決定）
- **影響**: 他サービスへの通知は Webhook で対応する

### 2026-10-02 — 通知設定は DB で管理（`.env` から移行）
- **判断**: Discord の URL・有効/無効・再通知の設定は、設定画面から変更できるよう DB に保存する
- **理由**: 記録なし（設定画面から変更できる形が望ましいという方針）

## データモデル

### 2026-10-02 — アラームは重要度 2 段階、しきい値は 4 項目
- **判断**: 軽故障（warning）と重故障（critical）の 2 段階。しきい値は「上限・下限」×「軽故障・重故障」の 4 項目
- **理由**: 「すぐ止めるべき」と「様子を見る」で通知先と通知音を分けたい、という現場の要望
- **影響**: 重要度が変わったときは新規アラームを作らず既存行を更新する（履歴が増えすぎないため）。3 段階以上が必要になったら再検討する

### 2026-10-02 — 不感帯（ヒステリシス）を導入
- **判断**: 発生は閾値超過で即時、解除は閾値から不感帯の幅だけ戻ったときに行う
- **理由**: 閾値付近で値が揺れると、発生と解除が繰り返されて通知が溢れるため

### 2026-10-02 — センサー削除は物理削除（関連データも削除）
- **判断**: センサーを削除すると、測定値とアラームも削除する。ウィジェットは残し、紐付けだけ外す
- **理由**: 論理削除にすると、削除済みと同名のセンサーを登録できず、利用者が混乱したため
- **影響**: アラーム履歴は失われる。監査目的で残す要件が出たら再検討する
- **注意**: DB の CASCADE だけでは不十分だった。SQLAlchemy が削除前に子行を読んで外部キーを NULL にしようとするため、`passive_deletes` を設定して DB 側の連動削除に任せている

### 2026-10-02 — ダッシュボードは論理削除のまま
- **判断**: ダッシュボードは `deleted_at` による論理削除を続ける
- **理由**: センサーと違い、同名での再登録の問題がない

### 2026-10-02 — 生産数は時間・日・目標達成率で表す（OEE は見送り）
- **判断**: 「直近 1 時間」「本日累計」「本日の目標達成率」を集計する。OEE は採用しない
- **理由**: OEE には停止理由の記録とシフトのカレンダーが必要で、現時点の非目標（複雑な生産管理は作らない）に反する

## 技術選定

### 2026-10-02 — DB は PostgreSQL のみ（SQLite は使わない）
- **判断**: 開発・テスト・本番のすべて PostgreSQL 15（テストも PostgreSQL に接続する）
- **理由**: 記録なし。以前は開発・テストに SQLite を使う想定だったが、現在は全環境で PostgreSQL に統一されている

### 2026-10-02 — TimescaleDB は見送り
- **判断**: 複合インデックス `(sensor_id, recorded_at)` で対応する
- **再検討の目安**: 測定値が 1,000 万行を超える、またはダッシュボードのクエリが 500 ms を超える

### 2026-10-02 — 画面の更新は 5 秒ごとのポーリング
- **判断**: WebSocket は使わない。一覧・最新値・アラームは 5 秒ごと、グラフの直近モードは 30 秒ごとに取り直す
- **理由**: 実装が単純。WebSocket は後続フェーズで検討する方針
- **再検討の目安**: 低遅延が必須の利用者が出たとき

### 2026-10-01 — ダッシュボードは自由配置（12 列グリッド）
- **判断**: `react-grid-layout` でドラッグ配置・自由なサイズ変更。軸の範囲も後から編集できる
- **理由**: 配置とサイズの制約が強すぎるというフィードバック

## 認証・SaaS

### 2026-10-04 — センサー名はワークスペース内で一意、取り込みキーは全体で一意
- **判断**: センサー名はワークスペース内で一意（self-hosted は NULL 用の部分インデックス）。取り込みキー（`ingest_key`）は全体で一意のまま
- **理由**: 名前の全体ユニークは、別のワークスペースが同じ名前を使えない不具合になっていた。取り込みAPIはキーだけでセンサーを特定するため、キーは全体で一意である必要がある
- **影響**: 別のワークスペースのキーと衝突すると 409 を返す。応答から、キーが使われていることが分かる（存在の確認になる）。ワークスペースごとにキーを分けるには、取り込みの形式を変える必要がある

### 2026-10-04 — 通知設定はワークスペースごとに持つ
- **判断**: 通知設定は、ワークスペースごとに1行。アラームは、そのセンサーのワークスペースの設定で送る。設定の無いワークスペースは Discord 通知をしない
- **理由**: ID=1 の1行に固定していたため、SaaS のアラームが他のワークスペースの設定で送られるおそれがあった
- **影響**: 再通知の判定も、ワークスペースの設定に従う

### 2026-10-03 — SaaS はマルチテナント（共有 DB + `workspace_id`）
- **判断**: テナントごとに DB を分けず、同じ DB でワークスペース単位に分離する
- **理由**: 記録なし（共有 DB + `workspace_id` による論理分離として決定）
- **self-hosted との関係**: `workspace_id` が `NULL` のデータが self-hosted。`AUTH_MODE`（`disabled` / `multi_tenant`）で切り替える

### 2026-10-03 — Free Tier の制限
- **判断**: センサー 10 個まで（超過は 402）。測定値は 90 日で削除（SaaS のセンサーのみ）
- **理由**: 記録なし（超過分は将来の有料プランで対応する方針）。self-hosted は対象外

### 2026-10-03 — 管理者アカウントは DB に入れない
- **判断**: 管理者はサーバーのテキストファイル（bcrypt ハッシュ）で管理する
- **理由**: 記録なし（運用者だけが扱うアカウントを、利用者データと分けて管理する方針）
- **影響**: ファイルは DB バックアップに含まれないので、別途保管する

### 2026-10-04 — リフレッシュトークンは使うたびにローテーション
- **判断**: 使ったトークンは即時失効し、新しいトークンを発行する
- **理由**: 盗まれたトークンの再利用を検出しやすくするため

## 外部連携（Webhook）

### 2026-10-04 — Webhook の新設（Phase 1）
- **判断**: イベント `reading.received`（値の受信ごと）と `alarm.triggered`（アラーム発生ごと）を、任意の URL へ JSON で送る
- **理由**: 拡張の主軸（上記 2026-10-01）を実現するための最小の仕組み
- **意図的に入れなかったもの**: 再試行、送信キュー、署名。必要になった段階で追加する

### 2026-10-04 — Webhook の送信先を制限（SSRF 対策）
- **判断**: `https` のみ。名前解決した全アドレスが公開 IP の場合だけ送る。登録時と送信直前の両方で検証する。リダイレクトは追わない
- **理由**: 利用者が指定した URL にサーバーから送るため、そのままでは社内ネットワークやクラウドのメタデータへアクセスされるおそれがあった（SaaS では他の利用者にも開かれる機能になる）
- **例外**: `WEBHOOK_ALLOW_PRIVATE_NETWORKS=true` で社内ネットワークを許可できる。自己ホストで社内の自動化基盤を使う場合だけ。既定は禁止
- **残るリスク**: DNS rebinding（検証と接続の間に DNS が変わる）は未対応。接続先の IP を固定すれば防げる

### 2026-10-08 — Webhook の送信は、接続を使い回し、同時送信と送信待ちに上限を設ける
- **判断**: 共有のクライアントで接続を使い回す。同時送信は 10 件まで、送信待ちは 1,000 件まで。超えた分は送らずに捨て、件数をログに出す（多くても 1 分に 1 回）
- **理由**: 値の受信ごと・アラームごとに送るため、大量の取り込みや送信先の遅延で、送信のタスク・DNS の検証（スレッド）・接続が際限なく増えていた。ラズパイの負荷テストでも、Webhook の送信が CPU を使った（下記「運用上の注意」）
- **影響**: 上限を超えると Webhook が届かないことがある（再試行はしない方針のまま）。確実な配送が必要になったら、送信キューと再試行を検討する

### 2026-10-04 — プラグイン基盤を廃止（Phase 2）
- **判断**: `app/plugins/`、`/api/plugins`、関連テーブル（`plugins` / `plugin_configs`）を削除する
- **理由**: 上記の方針（2026-10-01）に従い、利用者が使わない拡張の仕組みを残さないため。サンプルの `reading_logger` 以外に利用例は無かった
- **影響（破壊的変更）**: プラグインの設定値は失われる。downgrade はテーブル定義のみ戻し、データは戻らない

## 管理画面

### 2026-10-05 — 取り込みのレート制限は、管理画面から期限付きで解除できる
- **判断**: 管理者が管理画面から取り込みの制限を外せる。解除は既定 60 分で、期限が過ぎると自動で既定の制限に戻る。状態はメモリに持ち、DB には保存しない
- **理由**: 解除の切り替えのたびに、サーバーの環境変数を変えて再起動する手間をなくすため。「解除したまま戻し忘れる」事故を、期限で防ぐため
- **影響**: 再起動すると制限あり（既定）に戻る。環境変数が `off` のときは、画面からは変更できず、環境変数が優先される。単一インスタンス前提（レート制限のカウントと同じ）。解除・停止は管理者 ID とともにログへ残す

## データ移行

### 2026-10-04 — SaaS → OSS の移行は、書き出しファイルを介して行う
- **判断**: 移行元（SaaS）と移行先（OSS）を直接つながず、gzip の JSON Lines の書き出しファイルを介する。書き出しは SaaS の本人だけ、取り込みは OSS のみ
- **理由**: 両方が同じ DB に同時に存在する必要がない。ファイルは確認（件数の dry-run）と保管ができ、失敗しても何も残らない
- **影響**: 取り込み API に認証はない（OSS の前提）。インターネットに直接公開しないこと
- **後継**: 「2026-10-08 — self-hosted にも書き出しを足し、OSS → OSS を完結させる」（下記）

### 2026-10-08 — self-hosted にも書き出しを足し、OSS → OSS を完結させる
- **判断**: 「データ移行」の書き出しを self-hosted でも使えるようにする（全データ、
  `workspace_id IS NULL` を対象）。OSS → SaaS（ワークスペースを選んでの取り込み）は、
  このアプリではなく復旧ツール側で扱う（決定済み。「2026-10-08 — OSS 版 ⇄ SaaS 版は、
  所属を付け替えて書き戻す。今の DB の版は設定で明示する」、下記）
- **理由**: self-hosted の読み取り API はもともと認証が無く（architecture.md §11 の前提どおり）、全データが
  `GET` で読める。書き出しを足しても、読めるものが増えるわけではない。一方で OSS → SaaS は
  ワークスペースの選択・Free Tier の確認など、認証前提の判断が要るため、このアプリの
  無認証 API には置かず、運用者が操作する復旧ツール側に置く
- **影響**: self-hosted どうしの移行・バックアップが、アプリ内の「データ移行」だけで完結する。
  OSS → SaaS は引き続き復旧ツールが必要

### 2026-10-04 — ID と取り込みキーは保つ
- **判断**: センサー・ダッシュボードなどの UUID と `ingest_key` をそのまま移す。測定値の ID は振り直す
- **理由**: デバイス側の設定（取り込みキー）を変えずに済ませるため。測定値の連番は、移行先の連番と衝突させない
- **影響**: 同じワークスペースを同じ DB に取り込み直すと、ID が重なって失敗する（何も残らない）。削除済みのダッシュボードも行が残るため同様に失敗する

### 2026-10-04 — 測定値は差分の配列で書き出す（形式の版 2）
- **判断**: 測定値は、センサーごとに `[値, 前の行からの差分（マイクロ秒）]` の配列として、5,000 件ずつ1行に書く
- **理由**: JSON のキー名と ID を毎行書くと、約 14 バイト/件。配列と差分にすると約 6 バイト/件で、約 6 割減る。マイクロ秒を保つので、時刻は往復で完全に戻る（ミリ秒への丸めは見送り）
- **影響**: 版 1 のファイルは取り込めない。版 1 は未リリースのため、互換性は持たない

### 2026-10-04 — 通知設定とユーザーは移さない（通知設定は明示指定）
- **判断**: ユーザー・リフレッシュトークン・ワークスペースは移さない。通知設定（Discord の URL）は、`with_notifications` を指定したときだけ移し、移行先の ID=1 を上書きする
- **理由**: OSS には認証がない。通知の URL は移行先で意図的に設定するべき値

## バックアップ・復旧

### 2026-10-08 — 復旧ツールは本体と別のプログラムにする
- **判断**: バックアップの確認・書き戻しは、FactorEye の管理画面ではなく、別のプログラム（`tools/recovery/`）で行う。Docker があればどこでも動き、設定だけを変える
- **理由**: 不正アクセスでプログラムを壊されたときや、DB が壊れて backend が起動しないときこそ使う道具のため。インターネットに公開している画面に「バックアップを読む」「DB に書き込む」機能を置かないため
- **影響**: 画面は Basic 認証で、待ち受けは既定で 127.0.0.1。本番では本体と別の compose で動かし、本体のデプロイの影響を受けない

### 2026-10-08 — バックアップは、乗っ取られた本番で書き換えられている前提で展開する
- **判断**: SQL を自分で解釈せず、作業用の Postgres に流し込んでから調べる。流し込みは psql の `\restrict`・管理者ではないロール・秘密を渡さない環境で行う
- **理由**: sha256 の記録もバックアップと一緒に作り直せるため、検証だけでは改ざんを防げない。QA のレビューで、展開時に任意のコマンドが実行されうることが分かった
- **影響**: 所有者が管理者のロールのバックアップや、行頭にメタコマンドのあるバックアップは展開しない

### 2026-10-08 — 書き戻しは「無い行を足す」だけにし、試行と実行を同じ処理にする
- **判断**: 今ある行は変えない・消さない。試行は同じ処理を取り消す。実行は確認した件数と一致したときだけ、直前に今の DB を控えてから 1 トランザクションで行う
- **理由**: 復旧の操作で、今あるデータを壊さないため。件数の見込みと実際がずれる余地を無くすため
- **影響**: 「バックアップの時点の値に戻す（上書き）」はできない。必要なら控えと `infra/restore.sh` で丸ごと戻す

### 2026-10-08 — 測定値は（センサー, 時刻）で同じ行かを判定する
- **判断**: 測定値の連番の id は持ち込まず、（センサー, 時刻）が今の DB に無いものだけを足す
- **理由**: DB を作り直すと連番が最初から振られ、バックアップの id と別の測定値の id が重なるため
- **影響**: 同じセンサー・同じ時刻の測定値は 1 つとみなす

### 2026-10-08 — OSS 版 ⇄ SaaS 版は、所属を付け替えて書き戻す。今の DB の版は設定で明示する
- **判断**: OSS 版のデータは SaaS 版の選んだワークスペースへ、SaaS 版のワークスペースは OSS 版のデータとして入れる。今の DB が SaaS 版か OSS 版かは `TARGET_MODE` で指定する
- **理由**: 運用者から「止めるのではなく、できるように」との指示。版の判定をデータの中身で行うと、空の SaaS 版を OSS 版と取り違える
- **影響**: 書き戻しを使う場合は `TARGET_MODE` が必須。ユーザー・ワークスペースの行は付け替えのときは入れない

### 2026-10-08 — バックアップは権限 640、本番の外の控えは本番から消せない形にする
- **判断**: バックアップは所有者とグループだけが読める。S3 は「追加だけ」の鍵とバージョニング、別のマシンは本番から「読むだけ」の鍵（`rrsync -ro`）で取りに行く
- **理由**: バックアップには利用者のデータとパスワードのハッシュが入る。乗っ取られた本番から、外の控えを消されないようにするため
- **影響**: 復旧ツールのコンテナは、バックアップのグループ（`BACKUP_GID`）で読む

## ダッシュボード

### 2026-10-05 — グラフの時間範囲は Grafana と同じ操作にし、ダッシュボード単位で持つ
- **判断**: グラフは、過去への移動・現在への復帰・期間の変更（プリセットと任意の期間）・拡大縮小・ドラッグでの選択を持つ。時間範囲はダッシュボードに 1 つだけ持ち、SensorGraph と MultiSensorComparison は同じ範囲に従う。範囲は URL に保持し、ダッシュボードには保存しない
- **理由**: センサーの過去の変化を、前後の時間も含めて追えるようにするため。範囲をウィジェットごとにすると、比較グラフの時間軸がずれる
- **影響**: 長い期間の表示のため、間引き API（`/api/sensors/{id}/readings/downsampled`）を追加する。SaaS は 90 日まで。範囲の保存はしないので、開き直すと既定の「直近 1 時間」に戻る

## 性能

### 2026-10-05 — 一覧の応答は ORM を通さず、JSON を 1 回だけ作る
- **判断**: 測定値・アラーム・センサーの一覧は、必要な列だけを読み、Pydantic のモデルから JSON を 1 回だけ作って返す（`app/api/responses.py`）。OpenAPI の定義は `response_model` で残す
- **理由**: py-spy の計測で、CPU の大半は ORM のオブジェクト生成と、FastAPI の二重の変換（モデル → dict → 検証 → JSON）だった。読み出し 1 回あたりの作業を減らすため
- **影響**: 応答の形（camelCase の項目）は変わらない。列を追加するときは、一覧の列の一覧（`_LIST_COLUMNS` など）にも追加する

### 2026-10-05 — アラーム一覧はページングし、警告の表示は 100 件まで
- **判断**: `GET /api/alarms` に `limit`（1〜500、省略時は全件）と `offset` を追加する。警告の表示は、発生中と確認済みを、それぞれ新しい順 100 件まで取る
- **理由**: 全件の応答は約 210KB・約 0.4 秒で、取り直しのたびに CPU を使っていた（アラームが増えるほど重くなる）
- **影響**: API の既定の動きは従来どおり（全件）。`total` は、ページで区切る前の件数になった。警告の表示では、確認済みが 100 件を超えると、古いものは出ない（設定画面では見られる）

### 2026-10-05 — センサー一覧は ETag で 304 を返し、版ごとに JSON を保持する
- **判断**: 版（ETag）は件数と最終更新時刻から作る。`If-None-Match` が一致すれば 304（本体なし）。完成した JSON を版ごとにプロセス内に保持する（上限 32 件）
- **理由**: 画面と負荷テストが数秒ごとに全件を取り直し、300 件分の変換が CPU の大部分を使っていた。版が変わらない間は、読み出しも変換もやり直す必要がない
- **影響**: 版の判定は、件数と `updated_at` に依存する。センサーの変更は必ずどちらかを変えること（既存の更新処理は `updated_at` を更新する）。キャッシュとは、プロセスごとに持つ（ワーカーを増やすと、ワーカーごと）

## 配布（Docker）

### 2026-10-06 — frontend は Vite preview をやめ、nginx で静的ファイルを配信する
- **判断**: frontend の実行段は `nginx:alpine` にし、ビルド済みの `dist/` だけを置く。SPA のフォールバックと assets の長期キャッシュは `frontend/nginx.conf` で設定する
- **理由**: `vite preview` は開発用のサーバーで、devDependencies（約 200 MB）と Node.js を本番イメージに残していた。イメージは 428 MB → 63 MB になった
- **影響**: 実行時の API の URL は、引き続きビルド時の `VITE_API_URL` で決まる（変更するにはビルドし直す）。Vite 独自の preview の設定（`allowedHosts` など）は、実行時には効かなくなった

### 2026-10-06 — backend は多段ビルドにし、開発用依存は分ける。Alpine は見送る
- **判断**: 実行段には venv と本体だけを入れる。`requirements.txt` は実行時の依存、`requirements-dev.txt` はテスト・型検査・Lint・依存監査（`-r requirements.txt` を含む）。ベースは `python:3.12-slim` のまま
- **理由**: 開発用依存（mypy・pytest など）が約 100 MB を占めていた。多段ビルドと依存の分離で、イメージは 421 MB → 283 MB になった。`python:3.12-alpine` も試したところ 177 MB まで減ったが、musl 上での性能と挙動を確認できていないため採用しない（起動と `/health` の確認までは通過）
- **影響**: CI（backend-test）と README のチェック手順は `requirements-dev.txt` を入れる。Alpine に変える場合は、性能の計測（py-spy など）から行う

### 2026-10-12 — 復旧ツールのイメージから JIT と Perl を外し、各イメージから pip を外す
- **判断**: recovery は、postgresql-15 が引く LLVM（JIT）と z3、管理スクリプト用の Perl（perl 本体と perl-modules。`perl-base` の `/usr/bin/perl` は残る）を、`dpkg --purge --force-depends` と `llvmjit.so` の削除で外す。作業用の Postgres は `jit=off` で起動する（`entrypoint.sh`）。依存は多段ビルドで venv に入れ、pip は venv から外す（backend も同様）。backend は `uvicorn[standard]` をやめ、使う uvloop・httptools だけを入れる（websockets・watchfiles・PyYAML は不要）。pydantic の二重指定と、pydantic-settings が引く python-dotenv の明示指定も整理した
- **理由**: 実測（Mac arm64）で recovery は 512 MB → 299 MB（libllvm14 100 MB、libz3 21 MB、Perl 約 47 MB、pip 13 MB）。backend は 289 MB → 273 MB。本番（amd64）の recovery は 718 MB だったので、同程度の割合で減る見込み。作業用の DB は initdb・pg_ctl・psql・pg_dump を直接呼ぶだけで、JIT と Perl のスクリプトは使わない。クライアント・サーバーとも本番と同じ 15 系のまま（15.19）。recovery のテスト 72 件（作業用 Postgres への展開・書き戻しを含む）と、コンテナの起動・`/api/info` への認証つき応答、backend のテスト 300 件・ruff・mypy・`alembic upgrade head`・`/health` を確認した
- **影響**: recovery のイメージには apt の整合が崩れた状態（`dpkg --purge --force-depends`）が残るので、イメージの中で `apt` を使う作業はしない。Postgres を上げるときは、`llvmjit.so` の削除と `jit=off` が引き続き要るかを確認する。frontend は、未使用の依存が無く、イメージは dist を置くだけなので変更なし（バンドルの 785 KB の大半は recharts。遅延読み込みは別の判断）

## フロントエンド

### 2026-10-12 — 画面ごとに遅延読み込みし、vendor を分け、デプロイ後のチャンク失敗は 1 回だけ再読み込みする
- **判断**: ダッシュボード（`DashboardView`）・設定・セットアップガイド・管理者画面（`AdminApp`）・規約（`LegalPage`）と、recharts を使うウィジェット 3 種（`SensorGraph`・`MultiSensorComparison`・`StatValue`）を `React.lazy` で分ける。ログイン画面・ダッシュボード一覧・小さなウィジェット（`AlarmAlert`・`ProductionStatus`）は、初期表示に要る、または小さい（分けても往復が増えるだけ）ので分けない。`manualChunks` で `vendor-react`（react・react-dom・scheduler）と `vendor-charts`（recharts と d3 など推移的依存）を分ける。`index.html` は `Cache-Control: no-cache`（nginx.conf）。動的 import の失敗は、`lib/lazyWithRetry.ts` が 1 回だけ自動で再読み込みする（`sessionStorage` の印。読み込みに成功したら消す）。それでも失敗したら `ChunkErrorBoundary` が再読み込みの案内（`ErrorNotice`）を出す（チャンク以外のエラーは案内にせず、上へ投げ直す）。Suspense の fallback は既存の「読み込み中...」と同じ見た目
- **理由**: 実測（`npm run build`）で、単一チャンク 785 KB（gzip 232 KB）が、初期ロード（index + vendor-react）203 KB（gzip 65 KB）になった。内訳は index 60 KB・vendor-react 143 KB・DashboardView 98 KB・vendor-charts 419 KB（gzip 120 KB）・設定 26 KB・管理者 18 KB・ウィザード 8 KB。recharts（vendor-charts）は、グラフ系のウィジェットが画面に出る時だけ読み込まれる。vendor を分けると、アプリの更新で再取得されるのは index 側（60 KB）などになり、react と recharts は再訪時に再取得されない。デプロイのたびにチャンクのハッシュが変わるため、古い `index.html` を持つブラウザは、消えたチャンクを要求して失敗する（nginx は `/assets/` に 404 を返す。これは正しい）。`index.html` をキャッシュさせず、残った失敗は再読み込みで新しい `index.html` に切り替える
- **影響**: 画面を初めて開く時に、小さな読み込み待ちが 1 回入る（以後はキャッシュ）。新しい画面を足す時は、`lazyNamed` で分け、`Suspense` と `ChunkErrorBoundary` で囲む。自動の再読み込みはタブごとに 1 回（読み込みに成功したら、次のデプロイでまた 1 回）。ブラウザでの実画面確認と e2e は、この変更では行っていない（`vite preview` の配信と単体テストのみ）

## 運用上の注意

これまでの作業で起きた問題から、次の注意を守ること。

- **テスト DB を分ける**: backend のテストは、接続先のすべてのテーブルを作り直して削除する。開発用・本番用の DB に向けると、データが消える（実際に起きた）。テスト専用の DB を指定すること
- **`docker compose down -v` は慎重に**: `-v` はボリューム（DB のデータ）も削除する。実行前に `docker compose ps` で、自分が起動したコンテナかを確認する。他の人が使っている可能性のあるスタックには使わない
- **フレッシュな環境で一度は通す**: ローカルの使い回しの DB では、マイグレーション未適用やヘルスチェックの競合が見えない。CI のような空の環境での起動を、リリース前に一度行う（実際に、空の DB で起動できない不具合が見つかった）
- **マイグレーションは往復を確認する**: `alembic downgrade` と `upgrade` を通してから取り込む
- **Enum 型のマイグレーション**: `op.create_table` は Enum 型を自動で作るため、事前の `create()` は重複エラーになる。`add_column` は事前の作成が必要。挙動が異なるため注意する
- **バックアップは取ってから破壊的な操作をする**: DB を消す操作（テーブル削除・マイグレーションの downgrade）は、先に `infra/backup.sh` で取得する
- **利用者データを消すときは、外部キーの順に**: `refresh_tokens` → `widgets`（`dashboards` を参照）→ `workspaces`（連動して `sensors`・測定値・アラーム・ダッシュボードが消える）→ `users` の順。`NO ACTION` の参照があり、順番を誤ると途中で失敗する（トランザクションで囲み、件数を確かめてから確定する）
- **消した後は領域を戻す**: DELETE では、DB の使用量はすぐには減らない（PostgreSQL は領域を再利用するだけ）。表が空になったら `VACUUM FULL <表名>` で OS に返す
- **性能の計測は、アプリを変えずに行う**: `docker run --pid=container:<backend> --cap-add SYS_PTRACE` で、別のコンテナから py-spy を実行する。関数ごとの配分は近似（応答の変換は、どの API から来たかが分かりにくい）
- **負荷テストの前に Webhook の登録を確認する**: 負荷テストは閾値を超える値を多く送るため、アラームごとに Webhook が送られ、CPU を使う（実際に起きた）。テスト前に登録を確認し、不要なものは消す
- **センサーを更新したら `updated_at` を更新する**: センサー一覧の版（ETag）は、件数と `updated_at` で判定している（architecture.md §4.1）。更新で `updated_at` が変わらないと、古い一覧が返る
